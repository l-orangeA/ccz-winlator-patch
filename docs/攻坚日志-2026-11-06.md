## 1. 源码对照：8.0 vs 11.2 渲染组件

| 组件 | 8.0 | 11.2 | 结论 |
|---|---|---|---|
| `GLRenderer` | 无 swap 设置 | `EGL14.eglSwapInterval(display, 0)` | 已移植测试，**负优化**，弃 |
| `Texture` | `GL_BGRA` + `UNPACK_ALIGNMENT=4` | 同为 BGRA、alignment 1、owner API | 8.0 已是 BGRA，无需改 |

## 2. 卡顿取证（23.4 分钟 ftrace + 采样）

方法：
- `atrace --async_start -b 262144 sched gfx freq power` 环形缓冲；
- 设备侧每 2 秒采样 SF `--latency`、CPU/GPU 频率、内存、Top 进程；
- 分析最后 130 秒（4.6 GB 文本 → 过滤/位段现算）。

### 2.1 出帧

| 指标 | 数值 |
|---|---|
| 平均内容出帧 | 24.2 fps |
| 帧间隔中位 | 10–16 ms（60–100 fps 段） |
| 帧间隔 p90 | 28–200 ms |
| 每 5 秒窗口 | 6–21 次 >50 ms 空档 |

### 2.2 CPU 不是算力瓶颈

最后 130 秒按 8 核总容量折算：

| 进程 | 占 8 核 |
|---|---|
| Ekd5.exe（游戏） | 4.6%（≈0.37 核） |
| wineserver | 2.5% |
| surfaceflinger | 2.1% |
| GLThread | 1.4% |
| libtinyproot | 1.4% |
| Thread-5（X 服务） | 0.5% |
| composer | 0.5% |
| 内核回写 writer | 1.6% |
| 空闲（swapper） | 58% |

渲染链（GL+X+SF+composer）合计 ~4.5%，**不是瓶颈**。

### 2.3 游戏线程与 DVFS

- 游戏主线程 **7.4% 时间在 runqueue**，29% 睡眠；
- 工作形态：1 ms 小突发，单次上核中位 **0.23 ms**、p99 2 ms；
- 55% 时间落在 cpu6；卡顿开始时 **cpu6 = 400 MHz（最低档）**，卡顿过程中才爬到 600–1100 MHz；
- 同时 `migration/6` 迁移线程在跑；
- 大核中位 **600 MHz**；prime 1.2–2.6 GHz；GL 线程被排到**小核**（0–3，约 600 MHz）；
- FPSGO 目标帧率在 **10–60 之间乱跳**。

**结论：卡顿根因是「游戏单线程 1 ms 突发 + 大核 DVFS 长期 400–600 MHz + 频繁跨核迁移」。**

### 2.4 画范围/新格子的成本

点一下单位显示移动范围（0.23 秒窗口）：

| 线程 | CPU |
|---|---|
| **Ekd5.exe（GDI+box64）** | **0.42 s（≈183% 单核）** |
| GLThread（上传+绘制） | 0.12 s |
| Thread-5（X 光栅） | 0.06 s |

15 次连续“开/关范围”（13.6 秒）：
- 游戏 2.45 s、App 2.18 s，**线性、无退化**；
- App Native Heap 17.7 MB→17.7 MB；Dalvik 21.5→21.6 MB；游戏 VmRSS 201.0→201.0 MB；
- ⇒ **没有内存/句柄泄漏**。
- 同存档新读档 10 次开关：游戏 0.306 s/次、App 0.345 s/次。

### 2.5 上传减半实验（无收益）

把 `Texture.updateFromDrawable` 改成每两次上传一次（同场景读档）：
- 半上传：游戏 0.327 s/次、App **0.338 s/次**；
- 全量：0.306 / 0.345。
⇒ 上传不是 App 侧主成本，**不做脏矩形**。

### 2.6 磁盘 I/O

稳态 10 次开关：游戏/App 的 `rchar/read_bytes/syscr` 增量全为 0 ⇒ 资源已缓存，成本纯 CPU。

### 3.1 标题界面（1 秒）

### 3.2 战斗稳态（1 秒）

## 8. 探针/工具教训（本轮踩坑）

1. **smali 分支方向**：`if-gtz` 是“大于零跳转”，`if-lt v3,v4,:after` 是“小于则跳”。
   用反导致循环体一次不执行、探针不落盘、甚至除零崩 GLThread。本轮 `if-lt` 坑复现一次（opcode 直方图不写盘）。
2. **实例方法的参数寄存器**：`handleNormalRequest` 是实例方法，`p0=this`、`p1=client`；
   传 `p0` 触发 `VerifyError`（X 线程崩、游戏黑屏）。
3. **`.locals` 数量**：`<clinit>` 用 v1 但 `.locals 1` → `VerifyError: register index out of range`；
   且该错误只在 X 线程首次用时爆，表现为“游戏起不来”。
4. **短突发探针**：1 秒门槛 + 事件驱动写盘会漏掉 <1 秒的突发；改为**后台线程每秒落盘**。
5. **读文件竞态**：探针每秒覆写 3 KB，`cat` 可能读到半写状态（数值错位成 0x68000000）；读两次/校验总和。
6. **Wine 日志**：`WINEDEBUG` 被 `setupXEnvironment` 用 App 偏好覆盖；游戏进程 stdout/stderr → `/dev/null`，logcat 看不到 `+dib`。
7. **toybox taskset**：掩码按**十六进制**解析（`80`=cpu7，`f0`=cpu4–7），`0x80` 会报 bad mask。
8. **启动偶发黑屏**：约 50% 概率 VProtect 壳启动失败（无 Ekd5、19 KB 黑屏）；所有自动化都要重试 3–4 次。
9. **`Process.myTid()` 自钉**：App 对自己线程 `taskset` 是可行的（SELinux 放行），但 `run-as` 对 App 线程会 Permission denied。
10. **子智能体/后台任务**：设备 grep 4.6 GB 太慢，应 `adb pull` 回 PC 分析；长任务用后台并检查 output。

## 12. 组件源码调研（当晚补充）

4 路并行精读（Java 管线 / 原生 C / Wine GDI 全路径 / box64 dynarec），完整报告：
`report\流畅度与画范围-组件优化-研究.md`。要点：

- 画范围的 0.42s 游戏侧 CPU 落在 **win32u.so 像素循环被 box64 翻译**：SRCCOPY 已是每行
  memmove（box64 直调原生 ARM），而 SRCAND/SRCPAINT 掩膜 blit（do_rop_codes_line_32 逐 DWORD）、
  PATCOPY（memset_32 的 x86_64 分支是内联 rep stos，box64 只 8B/迭代）、DSTINVERT（逐像素 NOT）
  都是翻译慢路径。
- box64 对**显式 memcpy/memset 调用**直调原生 NEON（bridge 0xCC + isSimpleWrapper → call_n），
  对内联 rep/stos 与逐像素循环没有 fast path ⇒ **把 win32u 热循环改写成调 libc 是唯一量级杠杆**。
- 388 次/秒 SetClipRectangles 的来源查明：每帧 GetDC 后首笔 GDI 的 `update_dc`（dc->dirty）
  → wineserver get_visible_region 往返 + 客户端 XSetClipRectangles + dibdrv 重绑；
  App X 服务器对 opcode 59 是 `skipRequest()` 直接丢弃，成本全在客户端，可用缓存消掉（中风险）。
- 上传路径确认已最优：32bpp 时 `surface->bits == image->data` SHM 零拷贝，bounds 50ms 批量合并。
- App 侧仅剩：wineserver 钉大核（现在混跑 0-7 核）、xconnector jmethodID 缓存、copyAreaOp

- 待办第一步：`WINEDEBUG=+bitblt` + `WINE_HWBP_LOG=1` 实测游戏的 ROP/尺寸直方图（容器 envVars

## 16. 字体问题定位与修复（r109g，2026-11-07 凌晨）

用户反馈 r109f「字体不对」。取证与修复：

### 16.1 症状
- 原版构建：文字 = 宋体内嵌点阵（细、锐利、像素感）；r109f：文字变粗体平滑描边（黑体感）。
- 字体文件齐全（windows/Fonts 有 simsun.ttc/simhei.ttf/PMingLiU/方正粗黑宋简体）→ 不是文件缺失。

### 16.2 根因：重建版缺 fontconfig
- 对比二进制：原版 win32u.so 含完整 fontconfig.c（`FcInit/FcConfigSubstitute/FcFontList/...` +
  `libfontconfig.so.1` dlopen 字样）；r109f 没有（构建时 `--without-fontconfig`）。
- fontconfig 负责**字体族匹配**（宋体 → 正确字体文件），没有它 wine 的选字回退到别的文件 → 渲染成
  描边粗体。imagefs 里 ARM64 `libfontconfig.so.1` + `/etc/fonts/fonts.conf` 都在（box64 原生桥接加载），
  原版的 fontconfig 运行时是活的。
- 定位手段：strings 二进制取证（先误判成 assert，后又排除 syscall 配对——r109g 前还有一轮
  freetype dlopen 链路确认：标题栏两边字体一样、读档对话框才是文字密集的可复现对比界面）。

### 16.3 修复：r109g = r109f + `--with-fontconfig`
- 构建：`build_win32u_r109g.sh`（configure 加 `--with-fontconfig`，WSL 装 libfontconfig-dev；
  NDEBUG 注入同前）。校验：41 个 Fc* 字符串 + libfontconfig.so.1 字样 + 无 __assert_fail。
  md5 `2be1316c83d603c4defae8669fcc1dfb`。
- 验收：进标题 90s，读档对话框渲染 = 原版宋体点阵风格，**截图字节数与原版当年截图完全一致**
  （643271，PNG 同字节≈同像素）。已固化到手机。

### 16.4 结论与备注
- **重编 win32u 的三个必要条件**（缺一不可）：`--with-freetype` + `--with-fontconfig` + `-DNDEBUG`。
  canonical 配方 `build_win32u_r109g.sh`（r109f 脚本作废，以 r109g 为准）。
- 若用户想换 Android 原生字体（NotoSansCJK 等）：数据级操作——把 ttf/ttc 放进 imagefs 并在
  `files/imagefs/etc/fonts/fonts.conf` 加目录条目即可（fontconfig 已通），无需再编 wine。

## 19. box64 r111 干净复测（手机重启后）→ 整条重编路线正式判死（11-07）

## 21. ② 前置研究：box64 0.3.0 vs 0.4.4 信号语义 diff（2026-11-07）★

4 路源码精读（0.3.0=/tmp/box64-0.3.0src，0.4.4=/root/box64-0.4.4）+ 与 fix108 交叉核对。

### 21.1 fix108 已天然免疫的点
1. **int3 RIP 归一化自守卫**（signal_x86_64.c:2786-2800）：BPT_FIX 先 process_vm_readv 检查
   RIP 处字节==0xCC 才 +1。0.4.4 已给 RIP=int3+1（x86int3.c:497），那里非 0xCC → 自动跳过。
2. **单步/断点分类用 TRAPNO**（:2823-2835 switch(TRAP_sig)）：0.4.4 单步 TRAPNO=1=TRCTRAP ✔ 命中
   SINGLE_STEP 分支；int3 TRAPNO=3=BPTFLT → ExceptionAddress-1 = Windows 真硬件语义 ✔。
3. **SEGV 无视 err 位**（历史怪癖逼出的健壮性，只用 CR2==RSP 判据）——0.4.4 把 err 改成真反汇编
   判读写（signals.c:446-464, decopcode.c:384）对我们无影响。
4. RF 位（EFL bit16）与 TF（bit8）不冲突；CR2/si_addr 两版都原样透传。

### 21.2 真正嫌疑（按可能性排序）
1. **no_tf**（0.4.4 新增，signals.c:588/633 + x64run.c:86-97）：handler 返回后 TF 仍置位时首条指令
   不陷阱 → 单步计数失步 → 壳心跳失配 → 反复 re-arm —— **arms 1600→9856 暴涨症状完全吻合**。
2. **可延迟信号补投**（signals.c:266-331）：SIGTRAP 在 LOCK_PROT 临界区被排队，补投 ucntx=NULL、
   RIP=R_RIP —— 我们的 init_handler 对 NULL 的行为未定义。
3. **handler 执行路径**：0.4.4 默认 SEGV handler 也走 DynaCall（signals.c:545-550），db 命中时
   copyEmu2USignalCTXreg 直接回 dynarec（:583-592）不再 siglongjmp。
4. Double-SEGV exit(-1) 兜底被删（03:1563-1570）→ 卡住时静默死循环（=74s 黑屏不崩的观感）。

## 22. ② ntdll 适配实验（2026-11-07）★ 结案：0.4.4 路线终止

### 22.1 探针标定（推翻头号假设）
- tf3_test 在 0.4.4（作者版）：db=1 / trap0 eip=401645；**0.3.0 原版对照组：db=1 完全相同**。
- 结论：**POPF 置 TF 的单步在两版语义一致**（都只 trap 一次）——"no_tf 破坏多步"假设破产，
  壳在 0.3.0 上也是 db=1 却工作正常。探针无法区分两版。

### 22.2 真正根因（代码 diff + 行为双重确认）
**0.4.4 signals.c:1044-1057 在"重复 ACCERR 毛刺"分支加了 `relockMutex/unlock_signal/return`
——信号永不转发给 guest**（0.3.0 同分支是清状态后落空穿透到转发，signals.c:1522-1533）。
我们的监视页（ntdll 手动 mprotect PROT_NONE）在 box64 眼中正是"页表说 RW、实际 ACCERR"的毛刺场景：
- 0.3.0：毛刺 → 重试 → 重复 → **穿透转发** → sim 收到 SEGV = 命中 ✔（健康 44106 faults / 400 hits ≈ 110:1，
  即每个监视访问约 4 次故障的毛刺级联）
- 0.4.4：同样场景 → **吞掉** → 指令无限重试 → faults 16 万 / hits 25 ✔ 完美吻合失控循环

### 22.3 修复尝试（r112c/r113）
- r112c：摘除信号返回路径的 4 个 no_tf 写点（signal32.c:753/798 + signals.c:588/633）→ 探针 db 仍=1
  （预期内，两版本就一致），真机壳仍死。
- r113：在 r112c 之上把 repeated-glitch 分支改回落空穿透（对齐 0.3.0）→ **更早卡死**
  （<64 arms，进程睡死）——穿透的 SEGV 走进了 0.4.4 的下一层不兼容（handler DynaCall 执行 / 
  copyEmu2USignalCTXreg 直回路径 / sigframe RF+SS 差异之一）。
- r113 + INTERP_SIGNAL 组合：同样早期卡死。
- 踩坑：copytree 保留 mtime 导致增量 make 假成功（二进制 md5 不变）——改源码后必须 rm -rf build 全新配置。

### 22.4 终审判决
0.4.4 的信号路径与 ntdll hwbp 模拟的不兼容是**多层的**（毛刺吞掉 → 穿透后的 handler 执行/上下文
差异 → …），每修一层露出下一层，且壳对时序敏感使调试只能靠 4 分钟一轮的黑盒试错。
**非 1-3 天工作量，属开放式研究 → 终止。** 除非未来拿到 box64 上游对 32 位 wow64 信号路径的
重大重构版本，否则 8.0 + 0.3.0 + fix108 是终态。

## 23. ② 深挖第二层：EACCES 根因（2026-11-07）★ 诊断完成

fix109diag ntdll（md5 e62fb8c0，MPROT_FAIL 时 dump VMA + 替代 mprotect 序列）实测：

```
MPROT_FAIL page=8ae000 errno=13
MPROT_VMA 00790000-00ac9000 r-xs sortdefault.nls   ← 失败页在 NLS 共享只读文件映射内！
MPROT_ALT R=0 NONE=0 RW=13 RWX=13                  ← 只有写位请求 EACCES（内核语义正确）
```

- **0.4.4 的 wine 分配器把壳的栈页放进了 sortdefault.nls 的共享只读文件映射范围**
  （0x790000-0xac9000）。共享只读映射的 VM_MAYWRITE 被内核清除 → mprotect 提权 RW = EACCES
  （内核行为完全正确）。0.3.0 上壳的 arena 在 0x10000000，不碰 nls 映射。
- sim 的 MAP_FIXED 兜底（anon 重映射 + process_vm_readv 内容恢复）机械上有效（内容保留），
  但共享映射语义已坏 → 壳在 21s 干净退出（下一层原因）。
- 另发现：0.4.4 有单次 VirtualAlloc 尺寸上限（768MB err=8 / 512MB 成功；壳的 766MB 压线成功），
  且壳的巨区/栈地址与 0.3.0 完全不同（0x70a000 vs 0x10000000）。
- 编译器指纹：作者 0.4.4 = GCC 9.4.0 = 我们的（0.3.0 是 9.3.0）→ 配方惩罚假设削弱
  （r111 的 -44% 另有原因：作者私补丁或噪声；解包速度两版相同 40s）。

### 37.2 22.2 s 的三个关键事实

1. **19.8 s 不是架构死账，是 bug**：44,000 次页故障每次都命中 `if (RIP >= 0x10000000) { open/read /proc/self/maps + sscanf }`，
   单次 474 µs 里 96% 花在这段；proot 下每次 `open/read` 还要 tracer 停一次。门控（`WINE_HWBP_MODLOG`，默认关）后
   单次降到 4.4 µs。此前「19.8 s 结构性、只能拿 0.2%」的结论全部作废。
2. **五段账**（22.2 s）：wineserver 1.5 / 容器+loader 4.9 / 壳解包 8.0（7.1 纯 VM + 0.5 页故障）/
   加载段 6.9 / 测量 0.9。**没有安全可拿的成块空间**。
3. **加载段那 4.8 万次 read 是 wineserver RPC，不是文件 I/O**：`NtReadFile` 注入计数两轮为空；
   `WINEFSYNC=1` 负收益（6.9 → 8.6/9.3 s）。
