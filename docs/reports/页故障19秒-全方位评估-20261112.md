# 页故障 18.9~19.8 s 全方位评估（2026-11-12）

> 对象：解包期 `44,106` 次页故障的开销（拟合 `β = 385~480 µs/次`，合计 **19.8 s**，占解包 30 s 的 66%）。
> 本文只回答一个问题：**这 19.8 s 还能不能拿回来**。
> 结论先行：**不能**。但不是「试过了不行」，而是**四条通道各自撞在不同的硬墙上**，本文把每堵墙的证据列全。

---

## 0. 结论摘要

| 通道 | 能否消除 19.8 s | 硬墙 | 证据强度 |
|---|---|---|---|
| box64 JIT 插桩 | ❌ | JIT 块内无法同步投递 guest 异常 | ★★★★★ 四条投递路径全实测（§2.1） |
| 硬件断点（perf） | ❌ | proot tracee 上不产生事件 | ★★★★★ 11 个地址 `cnt=0`（§2.2） |
| `userfaultfd` | ❌ | Android 禁止非特权使用 | ★★★★★ 两个 uid 均 `EPERM`（§2.3） |
| proot 信号路径改造 | ❌ | 只有二进制、无源码 | ★★★★☆ 74 KB 的 `.so` 无业务字符串（§2.4） |
| 减少触发次数 | ❌ | 页粒度是硬约束 | ★★★★★ 本轮新增 99% 是读（§2.5） |
| 降低单次成本 | ❌ | 可改部分只占 0.2%（实测） | ★★★★★ 原生 1 µs vs 游戏 450 µs（§1） |

**唯一剩下的理论空间**：单次 450 µs 里如果有一部分花在**有源码的组件**（box64 / Wine）而不是 proot 内核路径上，理论上还能抠出一点。但这需要先做成本分解实测（§4），且上限不高。

## 1. 成本构成（**已实测，纠正旧模型**）

### 1.1 实测：原生 aarch64（app 域，无 proot、无 box64）

探针 `tools/cost_probe.c`（aarch64 static，`run-as com.winlatcn` 直接跑）：

```
uid=11140
C getpid            :     0.29 us/call
B mprotect 4KB pair :     0.75 us/pair   (0.37 us/call)
A SIGSEGV trip      :     0.99 us/trip   (n=5000)
```

### 1.2 对比：游戏内每次页故障 **≈ 450 µs**

| 项 | 实测 | 占 450 µs |
|---|---|---|
| 一次 SIGSEGV 往返（原生） | **0.99 µs** | 0.2% |
| 一次 `mprotect` 4 KB（原生） | **0.37 µs** | 0.08% |
| 一次 `getpid`（原生） | 0.29 µs | 0.06% |
| **剩余（proot + box64 + Wine）** | **≈ 449 µs** | **99.8%** |

⇒ **旧模型错了两次**：
1. 旧报告把「1~2 次 4 KB `mprotect`（含 TLB shootdown）」当作主要成本 —— 实测 **0.37 µs**，即使 2 次也只有 0.74 µs，占 0.16%；
2. 旧报告认为内核信号投递贵 —— 实测往返 **0.99 µs**。

**真正的成本在软件链**：`内核 → proot(tracer) → box64(sigframe + RunFunctionHandler) → Wine(trap_handler) → 再反向一次`。一次页故障要**走两遍**这条链（SEGV 一遍 + TF 单步 SIGTRAP 一遍）。

### 1.3 单次链路的 11 步（源码位置已核对）

| # | 动作 | 层 | 源码 | 量级 |
|---|---|---|---|---|
| 1 | 指令写/读栈页 → SEGV | 硬件 | — | ~1 µs |
| 2 | 内核投递给 tracer | 内核 | — | ~0.5 µs |
| 3 | **proot 处理 + `PTRACE_CONT`** | **proot** | 无源码 | **大** |
| 4 | 内核再投递给 Wine handler | 内核 | — | ~0.5 µs |
| 5 | `hwbp_rw_page_for` + `hwbp_match_write` | Wine | `virtual.c:4133/4141` | ~0.1 µs |
| 6 | 解锁页 `mprotect` | 内核 | `virtual.c:4150` | **0.37 µs** |
| 7 | `hwbp_push_delta` + 置 TF | Wine | `signal_x86_64.c:2633` | ~0.1 µs |
| 8 | **单步 → SIGTRAP → 再走 2~4** | **proot+box64** | — | **同 2~4** |
| 9 | 复保护 `mprotect` | 内核 | `virtual.c:4170` | **0.37 µs** |
| 10 | box64 构造 x64 sigframe + `RunFunctionHandler` | **box64** | `signals.c:926-1265` | **大** |
| 11 | Wine `init_handler` + 异常分发 | Wine | `signal_x86_64.c:2730` | 中 |

**结论**：可优化的只有第 5/6/7/9 步，合计 **≈ 1 µs**，占 0.2%。**其余 99.8% 在 proot 转发与模拟器/ Wine 的信号帧构造上。**

## 2. 四条通道的判死证据

### 2.1 box64 JIT 插桩（★★★★★）

在 push 翻译里插「ESP == Dr1?」，命中直接投 #DB，绕开页故障。2026-11-12 用干净 box64 0.3.0 源码实施，四条投递方式全部实测失败：

| 投递方式 | 实测 | 失败机制 |
|---|---|---|
| `emit_signal(..., si_code=0x4A57)` | `jittrap=0` / 卡死 | 私有 code 不走 TRCTRAP |
| `emit_signal(..., si_code=1)` | `jittrap == steps`、hits=1 | 首次调用即 siglongjmp，打断 JIT 执行流 |
| 置 guest TF | hits 1629 → **5** | `dynarec.c:185` 的 `ACCESS_FLAG(F_TF)` **强制切解释器**，JIT 块里的 CALL 再也不执行 |
| host `raise(SIGTRAP)` | `jitmark=0`、marker 留存 | 信号被 box64 的 host 信号层吞掉 |

**通道本身是通的**（文件 / mmap 都能实时拿到 Dr1：`seen=dr1=31f014`、`calls=1582 万`），死在「JIT 块内无法同步分发 guest 异常」。

### 2.2 硬件断点 perf（★★★★★）

理论上最优：4 字节粒度、`faults` 直接 44,106 → ~400。历史上分三层做过：

| 层 | 结果 |
|---|---|
| 权限（app 域对游戏 tid `PERF_TYPE_BREAKPOINT`） | ✅ `fd=3 errno=0` |
| 信号（perf → `SIGTRAP` 直投目标 tid） | ✅ M2-c PASS |
| 容器内→外通道 | ❌ `sendto` EACCES、`kill` EPERM；改用 mmap ring + 轮询后 ✅ PASS（head 到 1414） |
| **真正命中** | ❌ **11 个地址 `cnt` 全 0**（数据/堆/代码/JIT 页），helper 自检 196 万正常 |

**唯一变量是「目标进程是 proot tracee」**。可能机制（未坐实）：proot 的 ptrace/seccomp 抑制了 perf 断点交付。

### 2.3 `userfaultfd`（★★★★★，本轮新增）

`unprivileged_userfaultfd` 需要 `CAP_SYS_PTRACE`。本轮静态探针实测：

| 用户 | uid | `userfaultfd()` |
|---|---|---|
| shell | 2000 | **−1 / EPERM** |
| app（`run-as com.winlatcn`） | 11140 | **−1 / EPERM** |

`/proc/sys/vm/unprivileged_userfaultfd` 读取亦被拒。

### 2.4 proot 改造（★★★★☆）

`libtinyproot.so` 74 KB，`strings -n 4` 只输出 libc 符号（`getenv`/`strdup`/`lstat`…），**没有任何业务字符串**，`PROOT_*` 环境变量也一个都搜不到 —— 业务逻辑不在这个 `.so` 里（可能在 assets 解压的另一份，或已加密）。
即便拿到，改错会破坏路径重定向（整个容器失效）。**无源码 + 高风险，不可做。**

## 3. 本轮新实证：为什么「少触发」也不可能

### 3.1 「只拦写」实测失败（P0-B 的最终判定）

历史上 P0-B 只用 `err` 位判过，而 box64 会把 push 的读故障上报成写，所以那条证据不可信。本轮做了**真正的行为包**（`WINE_HWBP_WONLY=1`，切到 `get_unix_prot` 里已存在的 `VPROT_WRITEWATCH` 路径，读放行、写触发）：

```
wonl y=1   arms=64  faults=16  steps=16  hits=16  t=0.1
```

**壳在第 64 步就死了**。两个结论：

1. **壳会「读」Dr1 并期望 #DB** —— 只拦写必漏检，P0-B 彻底关闭；
2. **44,106 次里 99% 是读** —— 前 64 arms 只有 16 次写故障（正常同期约 2,500 次读写合计），写占比 ≈ 0.6%。

这个数据反过来解释了为什么「只拦写」当年看起来诱人却行不通。

### 3.2 页粒度是硬约束（数学）

| 量 | 值 |
|---|---|
| 监视点大小 | 4 字节（Dr1，`len=1`） |
| 页大小 | 4,096 字节 |
| 页内其他字节 | 4,092 |
| 实测触发 | 27.6 次/arm |
| 实测真命中 | 0.25 次/arm |
| **误报率** | **99.1%** |

若要「只触发真命中」，监视粒度必须是 4 字节 —— 只有硬件断点能做到，而它已判死（§2.2）。

**除非**壳的栈布局能让 Dr1 独占一页（不可能，栈是连续使用）。

## 4. 结论：可改的部分只占 0.2%

§1 的实测把「450 µs 花在哪」这个问题回答掉了：

| 可归因的层 | 单次成本 | 占 450 µs | 是否有源码 |
|---|---|---|---|
| 内核 `mprotect`（2 次） | 0.74 µs | 0.16% | 有，但已是最小粒度 |
| 内核信号投递（2 次） | ~1 µs | 0.2% | 无（内核） |
| Wine 比较逻辑（`hwbp_match_write` / `push_delta`） | ~0.2 µs | 0.04% | 有 |
| **proot tracer 转发** | **未知，占比最大嫌疑** | **≫** | **❌ 无源码** |
| **box64 sigframe + `RunFunctionHandler`** | **未知** | **≫** | 有，但这是「让 guest handler 能跑」的必要路径 |
| Wine `init_handler` + 异常分发 | 未知 | 中 | 有，但是语义必需 |

**即使把第 5/6/7/9 步全部优化到 0，也只省 0.2%，即 0.04 s。**

**唯一还剩的缝隙**：如果能证明 proot 占 50% 以上，且 box64 的信号帧构造占 30%+，理论上可以通过「让 Wine 不注册 guest 信号 handler、改由 box64 直接分发」来省掉一次 `RunFunctionHandler` —— 但这会改变 guest 的异常语义（壳自己也可能注册 handler），风险极高、收益上限约 5~8 s，且需要重写 box64 的异常分发。**不建议做。**

## 5. 若仍要在 box64/Wine 侧抠（上限 0.2%，仅备查）

| 编号 | 做法 | 依据 | 上限 |
|---|---|---|---|
| W1 | `hwbp_match_write` 只在 `hwbp_rw_page[]` 非空时跑 | `virtual.c:4145` | 极小 |
| W2 | `hwbp_push_delta` 缓存 opcode→delta 结果 | `signal_x86_64.c:2452` | 极小 |
| W3 | 跳过 `setup_raise_exception` 的 `save_context`（真命中才需要，400 次） | — | ~0 |
| W4 | `mprotect_range` 直接调 `mprotect`，绕过 Wine 的 vprot 包装 | `virtual.c:4151` | 小（省一次查表） |
| W5 | 减少 `hwbp_write_stats` 的文件写入（每 64 arms 一次） | `virtual.c:4440` | ~0 |
| W6 | 合并「解锁 + 复保护」为一次 `mprotect` | — | 不存在（必须是两个时刻） |

**合计上限**：0.2%（≈0.04 s）。**不建议投入。**

| 方向 | 证据 |

| 减少 arm 次数 | `faults` 由壳的访问次数决定，与 arm 无关 |
| 静态脱壳 | PC 端已 90% 判死（按需解密 + 虚拟化函数） |
| 多线程并行 | 壳状态机串行 |

## 7. 一句话总结

**19.8 s = 44,106 次 × 2 遍「proot tracer + box64 信号帧 + Wine 异常分发」的软件链，每次约 225 µs。**
不是 `mprotect`（0.37 µs）、不是内核（0.99 µs）、不是硬件。要消除它，必须让「触发」不经过这条链 —— 而三条替代通道（JIT 插桩 / perf / userfaultfd）全部实证判死。

**能改的部分只占 0.2%。建议把资源转向加载段（7.4 s）和容器启动（4.3 s），这 19.8 s 到此为止。**

## 9. 最终突破：那 19.8 s 是一段遗留调试代码（21:30）

前 8 节的结论是「死账」，**错了**。用分段计时继续拆 `sig_handler`，发现了一个 bug。

### 9.1 分段结果（Wine handler 内部）

| 段 | 位置 | 耗时 |
|---|---|---|
| `init` | 入口 → `hwbp_handle_rw_fault` 之前 | **474 µs（96.4%）** |
| `unlock` | `hwbp_handle_rw_fault` | 11.7 µs（2.3%） |
| `tail` | 之后 → `leave_handler` | 1.8 µs（0.4%） |

`arch_prctl`（`init_handler` 里唯一的 syscall）只占 **1.2 µs**，排除。

### 9.2 元凶

`segv_handler` 开头有一段**调试代码**：

```c
if ((ULONG_PTR)RIP_sig(ucontext) >= 0x10000000)
{   /* locate the module of a host-side fault */
    static char mb[262144]; int fd = open( "/proc/self/maps", O_RDONLY ), mn = 0, r;
    while (mn < (int)sizeof(mb) - 1 && (r = read( fd, mb + mn, ... )) > 0) mn += r;
    ...
    while (line && *line) { sscanf( line, "%lx-%lx", &lo, &hi ); ... }
}
```

壳的 `RIP = 0x31f014`，**大于 `0x10000000`**，所以**每次页故障**都会：
1. `open("/proc/self/maps")`
2. `read()` 最多 **256 KB**
3. 逐行 `sscanf` 解析

在 proot 下每次 `open/read` 都要 tracer 停一次，44,000 次 × 这个开销 = **那 19.8 s**。

### 9.3 修复

把这段用 `WINE_HWBP_MODLOG` 门控（默认关闭），生产路径不再执行：

```c
static int modlog = -1;
if (modlog < 0) modlog = getenv("WINE_HWBP_MODLOG") != NULL;
if (modlog && (ULONG_PTR)RIP_sig(ucontext) >= 0x10000000) { ... }
```

### 9.4 实测（同一台设备，同一套环境）

| 指标 | 修复前 | 修复后 |
|---|---|---|
| `init` 段 | 474 µs | **4.4 µs**（−99%） |
| 解包 `t` | 29.7~30.1 s | **7.2 / 7.3 / 7.7 / 8.0 / 8.5 s** |
| 启动到标题 | 44.5 s | **22.1 / 22.2 / 22.3 / 22.3 / 25.3 s** |
| `arms / hits` | 1536/384、1600/400 | 同样完整 |
| 游戏 | 可玩 | **可玩**（`Ekd5=8278` 在标题，截图 971474） |

**净收益：约 20~23 秒（47%）**。

### 9.5 稳定性

`nomod1~4` + `final_a/b` + `v1~3` 共 11 轮：**7 轮成功、4 轮卡死**（`arms` 停在 576/1088/1280/1472）。

- 卡死与本次改动**无关** —— 生产版同样卡（`ok2/ok3/ok4` 连续三次）；
- `clean_leftover=[]` 时也会卡，说明不完全是残留；
- 已改进清理顺序（先杀 tracer `libtinyproot.so` 再杀 tracee、`-9`、两轮），卡死率从 5/9 降到 1/3，但**未归零**。

**验收口径**：连续跑 3 轮，至少 2 轮到 22~25 s 且 `arms` 完整，即视为可用。

### 9.6 修正 §1~§8 的结论

| 之前 | 现在 |
|---|---|
| `mprotect` 不是瓶颈 ✓ | 仍然成立（0.37 µs） |
| 内核信号 1 µs ✓ | 仍然成立 |
| 「99.8% 在 proot+box64+Wine」✓ | 仍然成立，但**其中 96% 是这段调试代码**，不是架构成本 |
| 「19.8 s 是死账」❌ | **是 bug，已修掉** |
| 「四条通道全判死」✓ | 仍然成立，但**根本不需要换通道** |

⇒ **前面的排查方向没错，但漏了一件事：没有先怀疑「补丁自己有没有多余工作」。** 这是本项目的教训：**在归因于架构之前，先把每一段的实际耗时打出来。**
