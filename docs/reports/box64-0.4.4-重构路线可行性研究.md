> 本文是**可行性研究**，不是实施。纯读源码/资产，未编译、未部署、未动设备。
> 前置结论见 `box64-0.4.4-重构升级方案.md` §7–§11（黑盒补丁路线已按止损条件终止）。

## 0. 结论先行

| 路线 | 一句话 | 评级 |
|---|---|---|
| **A 信号路径重构** | 把 0.4.4 的 EFLAGS/TF 生命周期改成「单一权威源 + 所有返回路径统一同步」 | ★★★ 唯一能真正升级的路，但属上游级改造 |
| **B 局部 backport** | 把 0.4.4 的部分 dynarec 改进搬回 0.3.0，不碰信号层 | ★ 有硬阻塞，且收益存疑 |

## 1. 约束复述（来自前序实证）

1. 构建配置不一致会让结论完全失真：作者版 0.4.4 是 `ARM64=ON / ARM_DYNAREC=ON / BOX32=OFF` +
   显式 dynamic-linker 指向 imagefs；ntf 树是 `ARM64=OFF / ARM_DYNAREC=OFF`、linker 空（升级方案 §7.2）。
2. 根因链：Wine 清 TF 生效（`copy tf=1 → ctx tf=0`，探针 36 行），但 guest 永久单步 →
   `hits` 冻结 25（升级方案 §8–§10）。
3. 0.4.4 的 EFLAGS 有三处来源互相覆盖：内层 `old_eflags`、外层 `old_eflags`、宿主 ucontext `regs[26]`
   （`xFlags`）；主返回路径不写回宿主槽（升级方案 §10.1）。
4. 验收硬指标固定：`arms≈1536 / hits≈384` → 出标题 → 游戏存活 → 性能 A/B（>3 s / >5% 才认差异）。

## 3. 本轮新发现的两条硬阻塞

### 3.1 生产 0.3.0 没有可重建源码树（实证）

| 项 | 值 |
|---|---|
| 设备生产 box64 | `dd297b6d3b0966f6f8acf0d60495f82c`（= `box64.bak030`） |
| PC 侧同一二进制 | `device_backup/box64_test_20261105/box64_0.3.0_aarch64`，md5 同为 `dd297b6d…`，ARM aarch64 ELF，interpreter `/lib/ld-linux-aarch64.so.1` |
| `unpack_tools/box64-0.3.0.tar` | 只是 imagefs 打包（含 `usr/local/bin/box64`），**不是源码** |
| WSL `/tmp/box64-0.3.0src` 树 | CMake `ARM64=OFF / ARM_DYNAREC=OFF`、linker 空；产物 18.7 MB，md5 `4f9c18aa…` |

⇒ 该树可用于**静态源码对照**，但**无法重建出生产二进制**。任何 backport 都缺
「重建产物 md5 == 部署版」这一验收锚点（对比 fix110b 重建配方 §6 的严格程度）。
路线 B 的第一件事不是改代码，而是先找到/重建能产出 `dd297b6d` 的 0.3.0 源码 +
构建配置；这一步能否做到尚未验证。

### 3.2 0.4.4 的主要加速来源恰好不可单搬

`10~30%` 是 §20.1 的**估计值，从未实测**。按 §2 的依赖面，量级改进
（DynaCache 持久化缓存、hotpage 三态、custommem mixed-page 回退、arm64 后端重写）
全部与 env 体系 / 信号层 / dynarec 双向耦合；能单搬的只有 BIGBLOCK 改名、
`is_addr_autosmc`、BUILD_PASS 状态机、`updateflags_arm64*.c`，收益未知、估计 <5%。
⇒ 路线 B 的性价比很低。

## 4. 路线 A：信号路径重构（详细设计）

### 4.1 目标状态机：单一权威源

```
内核信号 → 宿主 ucontext p（regs[26] = guest EFLAGS）
  → box64 构造 x64_ucontext_t sigcontext（唯一交给 Wine 的可写副本）
  → Wine handler 修改 sigcontext（清/设 TF）
  → 返回前一次性同步：emu->eflags  AND  p->regs[26]
  → 所有返回路径（mctx2emu / siglongjmp / 正常返回）共用这个同步点
```

现状（§10）之所以坏，是因为 Wine 的修改只落到栈上 sigcontext，
内层/外层 `old_eflags` 各恢复一次，宿主槽又只在 3 个 dynarec 特殊分支写回。

### 4.2 改造点（file:line，逐项单变量）

| # | 位置 | 改动 | 验收 |
|---|---|---|---|
| **A0** | 构建 | 固定作者版配置（`ARM64=ON`、`ARM_DYNAREC=ON`、`BOX32=OFF`、显式 linker），产物 md5 锚定 | 重建可复现 |
| **A1** | `signals.c:538,566` | 删内层 `old_eflags` 无条件恢复，改为函数级单一保存 | `tf3_test` 语义与 0.3.0 一致 |
| **A2** | `signals.c:682,747` | 外层 `GO(eflags)` 不再恢复 EFLAGS（其余 `old_df/old_xmm/...` 保留） | 探针 `old/ctx/copy` 对齐 |
| **A3** | `signals.c:570,580,605,632` + `sigtools.c:835/854` | 抽 `sync_flags(emu, sigcontext, p)`，在 4 个返回路径统一调用；**主路径补宿主 `CONTEXT_REG(p,xFlags)` 写回**（目前只在 3 个 dynarec 分支有） | EFL_PROBE 日志里宿主槽 TF 与 ctx 一致 |
| **A4** | `signals.c:588,633`；`emu/x64run.c:89,859,965,1708,1775` | `no_tf` 改为基于「本次 TF 是否已消费」的显式状态机。**E10 已证实简单删掉更早死，必须重写而非删除** | 无 `TRAP tf=1` 无限循环 |
| **A5** | `signals.c:269-331` | `defer_signal` 对 SIGTRAP/SIGSEGV 一律不可延迟；或让延迟路径携带完整 sigcontext（现状补投时 `ucntx=NULL`） | `hits` 不再冻结 |
| **A6** | `signal32.c`（仅当将来 `BOX32=ON`） | I386_EFL=16 与 REG_EFL=17 的索引桥接；§8.2 的废弃 EFL_BRIDGE 补丁可作参考但需按 BOX32 路径重做 | 32 位探针 |

### 4.3 验收阶梯（每级不满足即停）

L0 构建可复现 → L1 探针语义 → L2 `hits≈384` → L3 出标题+读档+战斗 → L4 性能 A/B。
每级只改一个变量、独立结果文件、md5 锚定、可一键回滚（沿用 `p0_matrix.py` / `p0_restore.py`）。

### 4.4 工作量与风险

5–10 天，风险高：改的是信号框架，需要 dynarec 全量回归集（`tests/` 已有 4 个探针，
但不足以覆盖 TF/单步组合，需补）。最大不确定是 **§10.2 的落差**：
按源码 emu EFLAGS 应已 TF=0，实测 guest 仍 TF=1 —— 说明 A3 之外可能还有未识别的状态源。

## 5. 路线 B：局部 backport

- **硬阻塞**：§3.1，先补齐可重建 0.3.0 源码树，否则无法验收。
- 可搬清单：`BIGBLOCK` 命名回接、`is_addr_autosmc`、`BUILD_PASS` 状态机、`updateflags_arm64*.c`。
- 前提：逐处把 `BOX64*ENV()` 改回 ③ 的全局变量；`dynablock.c` 跳转表经本轮复核**不可单搬**（与 hotpage 三态耦合）。
- 收益：未实测，估计 <5%；要承担 dynarec 回归风险，性价比低。
- 评级 ★（不推荐，除非先解决源码树且接受低收益）。

## 8. 分阶段计划与止损

1. **Phase 0**：A0（构建配置固化）+ 补 0.3.0 可重建源码树（仅当并行做 B）；把 `tests/` 探针集补到覆盖 TF/单步。
2. **Phase 1**：A1→A2→A3 逐项，每步单变量 boot；EFL_PROBE 常驻取证。
3. **Phase 2**：A4（no_tf 重写）、A5（defer_signal），只在 Phase 1 仍无 `hits` 改善时做。
4. **Phase 3**：L3/L4 验收 → 部署链与回滚链（沿用 `p0_restore.py` / `final_restore.py`）。
5. **止损**：A3 + A4 各两轮仍无 `hits` 改善 → 终止，维持 0.3.0（与 §11.3 一致）。
6. **运维铁律**：卡死簇 → `adb reboot`；验收只用 prod 零日志 env；改源码后全新构建（copytree mtime 会让增量 make 假成功）。

### 10.3 三条待验证解释（都是假设，不是结论）

1. **走错了函数**：wow64 32 位信号（日志 `cs=23`）可能不走
   `my_sigactionhandler_oldcode_64`，而是 `my_box64signalhandler` 或另一条路径，
   我们改的代码没被执行。
2. **`defer_signal` 补投绕过**：`signals.c:278-331` 的延迟补投用

## 11. A3 取证与 A3B 验证（2026-11-08 14:1x–14:2x）

### 11.1 A3 只读探针（E14，`box64_A3PROBE.so` `4b7db667`）

在 A3 基础上打 9 个只读打点（前 120 事件/线程，写 `/home/xuser/a3probe.log`，零 env 改动）：

| tag | 次数 | 含义 |
|---|---|---|
| `oldcode` / `old64_in` / `a3_sync` | 各 128 | **信号确实进入我们改的两层函数** → 排除「走错函数」 |
| `defer_hit` | **0** | 排除「defer_signal 补投绕过」 |
| `tail` | 100 | 正常返回路径，`emu/sc/host` 三者 TF 全 0 |
| `jmp` | 27 | siglongjmp 路径（18 次 TF=0，9 次 SIGSEGV TF=1） |

关键序列（同一信号前后）：

```
h_sigaction ... host=34bbcd90(tf=1)   ← 信号进来时宿主 x26 = TF 1
a3_sync     ... sc=10202(tf=0) host=34bbcc90(tf=0)   ← A3 写回生效，变 0
tail        ... emu=10202(tf=0) sc=10202(tf=0) host=34bbcc90(tf=0)
h_sigaction ... host=34bbcd90(tf=1)   ← 下一次信号进来，又变回 1
```

⇒ **解释 3 成立**：`a3_sync`/`tail` 里宿主 x26 已被写成 TF=0，但 `siglongjmp`
恢复 callee-saved 寄存器（x26 是 callee-saved）把它覆盖回 setjmp 时的 TF=1。
这也解释了 A1–A3 为何零改善：写回发生在被覆盖之前。

### 11.2 A3B 验证（E15，`box64_A3B.so` `064dc6e3`）

在 A3 基础上把 `signals.c:580` 的 `if(emu->jmpbuf)` 改成 `if(0 && ...)`，
强制不走 siglongjmp、落到 `:632` 正常返回，让内核用我们改过的 ucontext 返回 guest。

结果：**+45 s 早死，无 `hwbp_stats`**。

原因（源码推断）：A3 只同步了 `xFlags`，没有同步通用寄存器与 PC；
绕过 siglongjmp 后内核用**旧寄存器/旧 RIP** 返回 guest → 立刻崩。
这反过来证明 siglongjmp 路径确实掌控 guest 恢复，且必须连同寄存器一起同步。

### 11.3 结论与下一步

- **已确定**：根因是「siglongjmp 覆盖宿主 x26」，不是函数走错、不是 defer、不是 EFLAGS 保存恢复。
- **正确的重构方向（A3-full）**：在 `:580` 之前用 `sigcontext` **完整**同步宿主
  `ucontext_t`（通用寄存器 + xFlags + guest RIP 槽），再决定是否 siglongjmp；
  不能只写 `xFlags`。
- **风险**：`CONTEXT_PC(p)` 是宿主 ARM64 PC，必须映射到 dynarec 的
  `native_epilog`/`native_next`，不能直接写 guest RIP。需要先读透
  `copyEmu2USignalCTXreg`（`sigtools.c:835`）与 `native_epilog` 的 PC 语义。
- **按止损条件**：A3 系列已多轮；A3-full 属于「换实现方式」而非「再修一层」，
  建议先做一次 `copyEmu2USignalCTXreg` + `native_epilog` 的语义评估，再决定是否实施。

## 13. A3D 与「完整魔改」的真实边界（2026-11-08 14:3x）

### 13.1 A3D（`box64_A3D.so` `ff472aac`）

把 `siglongjmp` 替换为：
```c
uintptr_t saved_pc = CONTEXT_PC(p);          // 信号进入时的宿主 PC
mctx2emu(emu, &sigcontext->uc_mcontext);     // Wine 改过的寄存器进 emu
copyEmu2USignalCTXreg(p, emu, saved_pc);     // 全量写回宿主 ucontext，PC 不变
return 0;                                    // 正常返回内核
```
结果：**进程存活 300 s、无任何 `hwbp_stats`、截图 19 KB 黑屏**，与 A3C 同型。

### 13.2 三种替换 siglongjmp 的方式全灭

| 方案 | 返回目标 | 结果 |
|---|---|---|
| A3B `064dc6e3` | 原 ucontext（只改 `xFlags`） | +45 s 早死 |
| A3C `06941283` | `native_epilog`（全量同步） | 黑屏、无 stats |
| **A3D `ff472aac`** | **原 PC（全量同步）** | **黑屏、无 stats** |

### 13.3 为什么都不行（源码层）

1. **32 位 guest 映射**：`copyEmu2USignalCTXreg` 按 64 位 guest 布局写
   `CONTEXT_REG(p, xRIP/xR15/...)`；当前 guest 是 32 位（`cs=23`），
   guest RIP 在 `emu->ip.q[0]` 低 32 位，映射关系与 64 位不同 → 寄存器状态错乱。
2. **宿主 PC 与 guest RIP 不是一一对应**：dynarec 的 native PC 只能通过
   `native_next`（dynablock 内下一块）或 `native_epilog`（带正确栈帧的退出）获得，
   不能拿 guest RIP / 原 PC 直接代替。
3. **siglongjmp 是唯一安全的「回到 EmuRun 主循环」机制**：绕过它就没有可用的 C 栈，
   一切「正常返回内核」的尝试都会落在半个 dynarec 帧上。
4. **真正的修复点**：`EmuRun` 的 setjmp 恢复分支——在 siglongjmp 回来后、
   进 dynarec/解释器前，强制 `x26 = emu->eflags`。这需要 ARM64 汇编 helper +
   精确 clobber 声明，并处理编译器对 x26 的使用。

### 13.4 结论：魔改的边界在这里

`signals.c` 层已彻底到头（A1→A3D 共 **8 个单变量实验**，无一改善）。
再往下是 **`dynarec.c` 的 `EmuRun` 恢复路径 + ARM64 汇编**，属于真正的「改引擎」：

| 项 | 评估 |
|---|---|
| 工作量 | 2–5 天（含回归） |
| 风险 | 高：改主循环可能引入普遍性回归（所有 64 位/32 位程序） |
| 前置 | 需要完整回归集：现有 `tests/` 只有 4 个探针，不足以覆盖 TF/单步组合 |
| 收益 | 仍不确定：修好 x26 后，`hits` 是否回到 384 未验证 |

### 13.5 若决定继续：唯一合理的路线图

1. 新增 `arm64_set_flags.S`：`mov x26, x0; ret`（或内联汇编 + clobber `"x26"`）。
2. 在 `EmuRun` 的 `if ((skip = SigSetJmp(...)))` 分支里，siglongjmp 返回后立即
   `arm64_set_flags(emu->eflags.x64);` 并声明 clobber，确保编译器不依赖旧 x26。
3. 先在 **64 位 guest 探针**（`tf3_test`）上验证不回归，再上 32 位壳。
4. 验收：`hits≈384` → 出标题 → 性能 A/B；任一不达标即回滚。

**在此之前，不建议再改 `signals.c`。**

### 17.3 污染源收窄

已排除：64 位 Set（WCTX64 无 `ffce115f`）、`restore_context`（RCTX32 0 行）。
剩余唯一会写 `amd64_thread_data()->dr*` 且**没有日志**的地方：

```c
/* get_thread_wow64_context，signal_x86_64.c:1413-1418 */

amd64_thread_data()->dr1 = context->Dr1;
...
```

- 若 `before` 已经是 `ffce115f` → 缓存早已脏，源头在更早的 Set/Continue；
- 若 `before` 正常、`after` 变 `ffce115f` → **Get 自己污染**，修复点就在 1413-1418。

之后才谈 Dr 修复；验收仍是 E19 `hits≈384`。

⇒ **显式写入全部排除，但缓存里仍有 `ffce115f`。**

### 19.2 关键结构：`cpu_data` 是「指针 + 偏移」

```c
/* signal_x86_64.c:486 */
static inline struct amd64_thread_data *amd64_thread_data(void)
{
    return (struct amd64_thread_data *)ntdll_get_thread_data()->cpu_data;
}
/* struct amd64_thread_data（:466） */
dr0 @0x02f0, dr1 @0x02f8, dr2 @0x0300, dr3 @0x0308, dr6 @0x0310, dr7 @0x0318,
syscall_frame @0x0328
```

`cpu_data` 是 `struct ntdll_thread_data` 里的内嵌缓冲区，`amd64_thread_data` 只是
把这块内存**按固定偏移**解释。若 0.4.4 的 TEB / `cpu_data` 大小或对齐与 Wine 期望不一致，
或相邻字段越界写，就会出现**只有个别字段（dr1）被污染、其它字段仍正常**的现象 ——
与全部观察吻合（`dr0=700`、`dr7=300504` 正常，唯独 `dr1=ffce115f`）。

### 19.3 下一步（静态可查，不用再跑设备）

1. 打印 `ntdll_get_thread_data()`、`cpu_data`、`&amd64_thread_data()->dr1` 三个地址，
   核对 `cpu_data + 0x2f8` 是否落在 TEB 的合法范围内；
2. 对比 0.3.0 / 0.4.4 box64 的 `NtCurrentTeb()` 返回值与 TEB 大小
   （box64 `os_wine.c:20` 用 `NtCurrentTeb()`，TEB 由 box64 提供）；
3. 在 `cpu_data` 前后加 guard 字段重编 ntdll，跑一次看 guard 是否被写穿。

### 19.4 阶段结论

Dr 污染已从「信号层 / TF 链 / 引擎恢复路径」一路追到「每线程 `cpu_data` 的内存布局」。
这是最后一条假设；若成立，修复点不在 `signals.c` 也不在 dynarec，而在
**box64 0.4.4 提供的 TEB 与 Wine `ntdll_thread_data` 的尺寸/对齐契约**。

## 20. 静态终审：TEB 假设不成立，到达工具链边界（2026-11-08 15:2x）

### 20.1 `cpu_data` 的尺寸契约

```c
/* unix_private.h:102 */
struct ntdll_thread_data {
    void *cpu_data[16];   /* 128 bytes, "reserved for CPU-specific data" */
    ...
};
```
而 `struct amd64_thread_data` 的最后一个字段 `syscall_frame` 在 **0x328**（808 字节），
远超 128 字节。但 `signal_x86_64.c:480` 的
`C_ASSERT( sizeof(struct amd64_thread_data) <= sizeof(((struct ntdll_thread_data *)0)->cpu_data) )`
在编译期通过 ⇒ 64 位构建下的 `ntdll_thread_data` 与 `unix_private.h` 里的这份不是同一份
（或 `cpu_data` 是更大缓冲区），**布局契约由编译器保证，不能从 box64 侧解释 `dr1` 单独错位**。

### 20.2 box64 不提供 TEB

两版 box64（0.3.0 / 0.4.4）全树 grep `NtCurrentTeb` / `GdiTebBatch`：**零命中**
（只有 LA64 后端的 `GETEB` 指令宏）。TEB 由 Wine 的 ntdll 分配，与 box64 版本无关。

### 20.3 结论：已到工具链边界

| 维度 | 结论 |
|---|---|
| 显式写入点（6 处） | 全部排除（§19） |
| CALL 路径（Set/Get/restore/Continue） | 全部排除（§15–§18） |
| TEB 提供方 | box64 不参与，两版一致 |
| 布局契约 | 编译期 `C_ASSERT` 保证 |

`ffce115f` 的唯一可能来源是**某处非显式写入**（`memcpy`、结构体整体赋值、越界写）。
要定位它，需要**硬件观察点**：

```
gdb -p <wine-pid>
watch *(unsigned long*)&amd64_thread_data()->dr1
```

在 proot + Android（无 root、无 ptrace 权限）环境下无法附加 —— 这是当前工具链的边界，
不是继续跑 boot 或加日志能解决的。

### 20.4 建议（三选一）

1. **接受 0.3.0**：当前 72 s 出标题、44.3 fps / p90 17.1 ms，组件级优化已到顶；
2. **上报上游**：把 §15–§19 的证据链（WCTX64/GCTXW/SETPROBE 三份日志 + 行号）
   提交给 box64 或 Wine，附最小复现（作者版 0.4.4 + fix110c + 该壳）；
3. **换调试环境**：在可 root 的桌面 Linux（x86_64 + wow64 或 ARM64 开发板）上
   用 gdb watchpoint 复现，定位后再回移到手机。

在此之前，不再对 Dr/TF 链路做任何改动。

设备四件套 md5 全对、生产态已恢复；WSL 官方树 `a7360b1e`、0 处补丁；攻坚日志未改。
