# 研究：壳的解密能不能做成多线程并行来加速？

日期：2026-11-02　范围：**纯静态分析，未改动任何设备**。样本：`Ekd5_orig_backup.exe`（= 平板上运行的 `Ekd5.exe`，同 md5）。

## 1. 先给结论

**不能。而且就算能，"并行"省下的也只是毫秒级。**

真正吃掉 46 秒的不是"解密的算术量"，而是**壳用一个 VM 解释器逐条执行解密逻辑**——
有效载荷只有几百 KB，46 秒意味着平均每个字节要跑几千条 VM 指令。
多开几个线程最多把这几百 KB 的算术再分摊一下，而算术本身只占其中的万分之一。

## 2. 静态证据

| 观察 | 数据 | 说明 |
|---|---|---|
| 区段 | 5 段，其中 4 段名为 `VProtect` | 典型 VProtect 布局 |
| 载荷体积 | `VProtect`#1 raw 0x58200 (360 KB)、#2 raw 0x6a400 (434 KB)；主代码段 VSize 0x16c198 (1.42 MB) 但 raw 只有 2 KB | 文件里的代码是"空壳"，实际内容运行时才填 |
| 熵 | 主段 7.73、VProtect#2 7.92（接近随机） | 已加密/压缩，不是可直接执行的代码 |
| 入口 `0x16f7d0` | 反汇编出来是乱指令（`arpl`/`out`/`fsubr` 混杂） | 入口本身也是密文，执行前先自解密 |
| 壳的 API 名表 | `CreateThread`、`SuspendThread`、`TerminateThread`、`SetThreadPriority`、`IsDebuggerPresent`、`OutputDebugStringW`、`Sleep`、`CreateMutexW`、`CreateWindowExW`、`GetPrivateProfileIntW`… | 线程相关 API 是**成组出现**的，配套的是反调试三件套（IsDebuggerPresent / OutputDebugString / Suspend+Terminate）→ 用途是反调试看门狗，不是并行解密 |
| 运行时（此前实测） | unpack 阶段进程 `Threads: 1`、CPU 持续 ~100%；1600 次断点装载、4.4 万次被监视访问 | 全程单线程且算力打满，不是等待/睡眠 |

## 3. 为什么"并行"在这里没有用武之地

分三层看：

**(1) 宿主层 —— 原理性不可分**
壳的代码是 guest 里的**单线程 x86 程序**。box64 只能把一个线程的指令流放在一个核上跑；
宿主无法把一个状态机的指令拆到多核（这不是配置能解决的，除非改程序本身）。

**(2) 算法层 —— 状态机天然串行**
即使去读壳的实现，解密也是由 VM 字节码驱动的：第 N+1 步依赖第 N 步的寄存器/栈状态。
只有当算法是"每块独立密钥 + 无链式依赖"时才谈得上并行——VProtect 这种壳几乎不会这么设计
（它要的正是"整体必须顺序执行"这个性质来做完整性校验）。

**(3) 收益层 —— 算一下就明白**
- 需要处理的载荷：约 0.4~1.4 MB
- 实测耗时：约 46 s ⇒ **有效吞吐只有 9~31 KB/s**
- 同样体积的明文解密（XOR/AES/查表），native 单线程至少 **100 MB/s**
- 也就是说：**解释器把这件事拖慢了约 3000~10000 倍**，而并行只能再除以 4~8。
  - 单线程 native：46 s → **约 10 ms**
  - 8 线程 native：46 s → **约 1.5 ms**
  - 8 线程但仍走 VM：46 s → **约 6 s**（还是慢 400 倍）

所以"多线程并行解密"这个方向，投入产出比极差：它优化的是那个几乎不占时间的部分。

## 4. 如果真要把 46 秒拿掉，只剩两条路（都不在本研究范围内）

1. **脱壳**：把算法逆出来、native 重实现/直接跑解包后的镜像。收益 46 s → 毫秒级。
   代价是完整脱壳工程，且属于**绕过软件保护**（只适合自己正版自用，不能分发）。
2. **接受现状**：靠"别退出进程"把 46 s 变成一次性的（切后台回来实测 3 s）。

## 5. 有没有"不脱壳但能快一点"的合规空间

有，但都很小：
- **单核主频**：壳是单线程算力活，理论上钉到最高频的 X3 最划算；但实测单核亲和会让 proot 死锁（5 次卡 2 次），
  折中做法是"只把游戏的**主线程**钉到 X3，其余线程放开"（需要容器内 taskset；属于设备实验，本次未做）。
- **box64 翻译效率**：已试遍安全开关，收益 2~5%，见 README 第 9 节。
- **反调试心跳开销**：我们的软件断点补丁只占 1.3~4.4 s（4.4 万次异常），再怎么优化也就省几秒。

---

**一句话**：这 46 秒是"VM 解释器执行解密逻辑"的成本，不是"加密算法本身的计算量"；
并行化只能作用于后者，价值在毫秒量级。要真正大幅缩短，只能脱壳（越界）或接受它。
