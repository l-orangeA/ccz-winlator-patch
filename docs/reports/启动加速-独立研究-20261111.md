## 【要点摘要】

- ★ **核心结论**：启动慢的主因不是游戏在算，是补丁的页保护在反复跑腿。`t = 0.004424·arms + 0.000450·faults`（RMSE 0.08 s）；**44,106 次页故障 × ~450 µs ≈ 19.8 s，占解包 26.8 s 的 74%**，纯 VM 计算只有 7.1 s。旧报告用猜的 30~100 µs 判死「Wine 侧只有几秒天花板」，**判死依据错了**。
- ★ **44,106 faults / 400 hits = 99.1% 误报**：整页 `PROT_NONE` 让任何栈访问都触发「SEGV + mprotect + 单步 + 复保护」，经 proot ptrace 转发。杠杆是**减少事件对次数**，不是优化翻译或提频。
- ★ **β 六组实机验证 385~480 µs**（11-09 449.5；11-11 428.2 / 480.4 / 480.3 / 396.2 / 384.9）。解包期 CPU 只占 55~62% 墙钟、`stime` 占 CPU 30~40%、ctxt switch ~2000/s ⇒ 时间花在等 tracer。
- ★ **P0-A 权限 / 信号 / 通信三层已全部打通**（15:50–16:30）：app 域能对游戏进程开 `PERF_TYPE_BREAKPOINT`；`F_SETOWN_EX`+`F_SETSIG(SIGTRAP)` 能把 SIGTRAP 直投目标线程；proot 会把外部 SIGTRAP 原样转发给 tracee；**容器内外 Unix socket 路径互通**（helper 在 `imagefs/tmp/` bind，ntdll 用 `/tmp/hwbp.sock` 连）。剩下纯 ntdll 集成。理论收益 **42.6 s → ~23 s**。
- ★ ~~零改动、用户感知最大：保活不退出（切后台 3.0 s）~~ → ⏸ **用户 16:02 暂缓**（「这个有些问题，先记着」），方案存档在 §5，不列入本阶段推进。
- ★ **15:40 已恢复生产态、120Hz 保留**：fix110b / r109g / r112b 三件套 md5 全对、生产 env 六项到位、preset=COMPATIBILITY；APK 保持 `fr120`，`graphicsDriverConfig`/`showFPS`/`name`/`drives` 原样。恢复后干净启动稳定 **54.8~56.0 s**，`arms=1600/hits=400` 完美档案、可玩。

## 2. 核心发现：26.8 s 里 19.8 s 是页故障，不是 VM 指令

### 2.1 数据（`boot_clean_20261109.log`，ntdll 内部 `CLOCK_MONOTONIC` 计时）

23 个采样点，形如 `arms=... faults=... steps=... hits=... t=...`。前 18 点严格匀速（每 64 arms 恒定 +2,576 faults、+1.4 s），末尾 5 点 faults 速率骤降 —— 这段「自然对照」让两个变量可以分离。

### 2.2 拟合公式（最小二乘，2 参数，全部 23 点）

```
t = 0.00442362 · arms + 0.00044955 · faults
max |残差| = 0.16 s    RMSE = 0.08 s
```

| 项 | 值 |
|---|---|
| 每 64 arms 的纯 VM 成本 | 0.283 s |
| **每次 fault 成本** | **449.5 µs** |
| 1,600 arms × 0.00442362 | 7.08 s |
| 44,106 faults × 0.00044955 | **19.83 s** |
| 合计 | 26.91 s（实测 t=26.8 ✓） |

### 2.3 不用拟合也能得到的交叉验证（差分法）

取拟合给出的「纯 VM 基线 0.283 s / 64 arms」，对末尾自然对照段逐段扣减：

| 区间 | Δarms | Δfaults | Δt | 扣除 VM 基线后 | 折算 |
|---|---|---|---|---|---|
| 前段典型区间（如 128→192） | 64 | 2,576 | 1.4 s | 1.117 s | **434 µs/fault** |
| 1152→1216 | 64 | 16 | 0.3 s | 0.017 s | 基线吻合 |
| 1216→1344 | 128 | 976 | 1.0 s | 0.434 s | **445 µs/fault** |
| 1344→1472 | 128 | 1,286 | 1.2 s | 0.634 s | **493 µs/fault** |
| 1472→1600 | 128 | 32 | 0.4 s | −0.166 s | 末段 VM 工作量变小（最大残差来源） |

三种算法给出 **434 / 450 / 493 µs**，一致。

### 2.4 稳健性 / 已知弱点（明说）

- 前 18 点 `arms` 与 `faults` 严格共线，β 主要由末尾 5 点决定；末段 VM 每步工作量可能变小 → β 有高估风险。
- **敏感性分析**：保守取 β=200 µs，补丁开销仍为 8.8 s（占解包 33%）；只有 β≤100 µs 才落回旧报告 1.3~4.4 s 的上界，而三种算法实测是 434 / 450 / 493 µs。
- `steps ≈ faults`（43,006 / 44,106）严格共线，无法把「SEGV」与「单步 TRAP」成本分开；但二者是同一次事件对，减少 faults 就同时减少 steps，工程结论不变。
- `t` 是墙钟时间，含 proot tracer 往返与调度等待；450 µs 对 native SIGSEGV（~5–20 µs）高出 20 倍以上，与 `proot可行性评估.md` §4「tracer 截停每一次信号转发」一致。

### 2.5 与既有实测的互证

| 观察 | 解释 |
|---|---|
| 锁频实验 `41.8 s vs 42.6 s` 无改善（§36.6） | 若瓶颈是 CPU 指令，prime 从 1.2→3.35 GHz 应有明显收益。零收益 ⇒ 瓶颈在内核/ptrace 往返，非 CPU 频率。**与本节结论一致** |
| `Ekd5` voluntary ctxt switches 30,000~43,800 次/秒（proot 报告 §追加） | 与「44 k 次事件对 / 26.8 s ≈ 1.6 k/s」同量级的停点风暴 |
| 解包速率全程恒定 1.4 s / 64 arms，无减速 | 排除 DVFS 掉频、cache 累积、内存压力；是固定工作量的线性循环 |

> ⚠️ 顺带纠正 §36.6「锁频否定」的一处测量缺陷：`boot_fixedperf_20261109.log` 显示 policy4（cpu4-6）仍有 60.5% 时间在 1.0 GHz，而游戏亲和是 `4-7`。**实际运行核未必被提频**。该结论方向仍与本节一致，但严格 A/B 应补 `cpuListWoW64=6,7` + 锁频组合。

### 2.11 页故障成本的结构与「魔改」空间评估（20:20 读源码）

**单次故障的完整成本链**（`src/fix110b/virtual.c` + `signal_x86_64.c`）：

| 步骤 | 动作 | 成本 |
|---|---|---|
| 1 | SEGV → proot（tracer）停止 → `PTRACE_CONT` 转发 | ~1 次 ptrace 往返 |
| 2 | `hwbp_handle_rw_fault`：`set_page_vprot_bits` + `mprotect_range` → `mprotect_exec`（inline `mprotect`） | **1 次 mprotect（4 KB，含 TLB shootdown）** |
| 3 | `hwbp_push_delta`（读 1~4 字节、几次比较）+ 置 TF | 极轻 |
| 4 | 单步 → SIGTRAP → proot 再停一次 → 转发 | ~1 次 ptrace 往返 |
| 5 | `hwbp_step_end_ex(keep)`：命中 400 次走 `keep=1`（**0 次 mprotect**）；误报 43,706 次走 `keep=0`（**再 1 次 mprotect**） | 0~1 次 mprotect |
| 6 | `setup_raise_exception`（仅真命中 400 次） | 轻 |

⇒ **每次故障 ≈ 2 次 ptrace 往返 + 1~2 次 4 KB `mprotect`**。`hwbp_push_delta`、`hwbp_match_write` 都是轻量操作，**不是瓶颈**。

**次数能不能减？不能。**
- 44,106 次 = 壳对**整个栈页**的访问次数，只有 400 次落在 `0x31f014`
- `mprotect` 的最小粒度是 4 KB，**无法只保护那 4 个字节**
- 唯一能做到「只监视 4 字节」的硬件断点（perf）已在 §5 判死
- 硬件层面 ARM64 不支持 4 KB 拆 64 B 子页

**成本能不能降？源码层面只有三条路，都不划算：**

| 方案 | 理论上能省 | 硬障碍 |
|---|---|---|
| A. 改 proot：信号不经过 tracer（`seccomp` user-notif 替代 ptrace） | 2 次往返 ≈ 30~80 µs/次 | **项目里只有 `libtinyproot.so` 二进制，无源码**；改错会破坏路径重定向 |
| B. **box64 JIT 插桩**：翻译内存访问时插「地址 == Dr1?」检查，彻底绕开页故障 | 可把 19.8 s 全消掉 | **生产用的 box64 0.3.0 没有完整可重建源码树**（`/root/box64-0.3.0src` 只有安装物）；0.3.8/0.4.4 有源码但与 VProtect 反调试不兼容 |
| C. 减少 arm 次数 | 0 | 故障次数由壳的访问次数决定，与 arm 次数无关 |

**⚠️ 意外发现（可能比魔改更值钱）**：单核实验里 `cpuListWoW64=4` **没有生效**（`Cpus_allowed_list` 仍是 `0-7`，与 §36.7 记录一致），但那一轮跑出 **43.1 s** —— 今天最快，`64arms VM` 只有 0.124 s（11-09 基线是 0.283 s）。同一套配置，今天其他轮次是 49.8~56.1 s。

⇒ **设备状态波动（43~56 s）远大于任何配置差异**，这很可能才是「有时快有时慢」的真正来源，值得优先查（温度/后台/页缓存），而不是继续啃 19.8 s 的死账。

### 2.13 基于 box64 源码的独立研究：把页故障从 JIT 层拿掉（20:40）

**读源码确认的三件事**：

1. **box64 完全没有 Dr 寄存器支持**：全树 `grep dr0/dr1/dr6/dr7` 只命中 `dladdr1`。⇒ 现在那套「Dr 语义」全靠 Wine ntdll 的 `hwbp_*` 补丁在**页故障**上伪造。
2. **box64 有完整 TF 单步支持，且在 `box64_wine` 模式下主动配合**：
   `dynarec_arm64_00.c:1499` → `if(box64_wine){ TBZ_NEXT(xFlags, F_TF); jump_to_epilog(dyn, addr, 0, ninst); }`
   ⇒ guest TF 置位时 box64 会退出 dynablock 让 TF 生效。现有补丁正是靠这个工作。
3. **壳的 400 次命中全是栈操作**：`hwbp_push_delta` 的存在、以及 `hits=400` 全部服务 push/call 类。而 box64 的 push/pop 翻译**只集中在 6~8 处**：
   `case 0x50-0x57`（636–643 行）、`case 0x68`（808 行）、`case 0x6A`、`case 0x9C`、`case 0xE8`（call rel32）。

**⇒ 新方案（比「全量内存访问插桩」小一个数量级）**：只改 push 类翻译，在 JIT 里直接投递 #DB，**完全不碰页保护**。

| 步骤 | 做法 |
|---|---|
| 1. 跨层传递 | box64 导出 `volatile uintptr_t box64_hwbp_watch;`（默认 0）；Wine ntdll 的 `hwbp_update` 用 `dlsym(RTLD_DEFAULT, "box64_hwbp_watch")` 拿到并写入 Dr1（同进程，可行） |
| 2. JIT 检查 | 每个 push 翻译处插入：算新 ESP → `CMPx_REG` 与 watch 比较 → 相等则调 helper 投递 guest #DB（或 `emit_signal(SIGTRAP)`） |
| 3. 语义对齐 | 现有补丁在 push **之前**回滚 ESP（`hwbp_push_delta`），JIT 里要复现同样的 RIP/ESP 状态，否则壳的校验会失败 |
| 4. 开关 | 环境变量控制，只在解包期启用；游戏运行期关掉，避免 push 多 3~4 条指令影响帧率 |

**预期**：44,106 次页故障 → **0**，19.8 s 基本全消。代价是 push 翻译多 3~4 条 ARM 指令（解包期可忽略）。

**已排除**：`BOX64_NOSIGSEGV=1` 实测**直接卡死**（`arms` 无、60.8 s）—— box64 的 SEGV handler 是必需的（负责 host SEGV → guest 异常转换，`signals.c:1123`），不能去掉。

**工程量评估**：push 类 6~8 处，每处加比较 + 条件跳转（box64 emitter 有 `CMPx_REG`/`B_COND`），**可行**。最大风险是语义对齐（ESP/RIP 在 push 前后的状态），需要用现有 `hwbp_stats` 的 `hits=400` 做验收。

### 2.19 Pass 2 根因坐实：JIT 块内无法同步投递 guest 异常（19:40，**判定终止**）

按单变量原则把「命中 → #DB」拆到底，四条投递路径全部实证判死。

**架构事实**（`readelf -h`）：`ntdll.so` = **x86-64 ELF**，`box64` = **AArch64 ELF**。Wine 是 guest，被 box64 解释/JIT 执行；跨层不能直接调函数，只能走 box64 的信号链。

| 投递方式 | 单变量实测 | 判据 |
|---|---|---|
| `emit_signal(..., si_code=0x4A57)` | `jit7b` 卡死、`jit7c` `jittrap=0` | 私有 code 不走 TRCTRAP，没到 Wine |
| `emit_signal(..., si_code=1)` | `jit14`：`jittrap=42990 == steps`、hits=1 | 第一次调用就 siglongjmp，打断 JIT 执行流，插桩自身失效 |
| 置 guest TF | `jit13`：`jittrap == steps`、hits 从 1629 掉到 5 | **`dynarec.c:185` 的 `ACCESS_FLAG(F_TF)` 强制切解释器**，JIT 翻译块里的 CALL 从此不再执行 |
| 真实 host `raise(SIGTRAP)` | `jit15`：`jitmark=0`、marker 文件留存、`vctx` 75k→320k；`jit16`：`jittrap == steps`、hits=28679 | 信号发生了但被 box64 的 host 信号层吞掉，没进 Wine 的 `trap_handler` |

**根因**：`CALL(native_hwbp_check, -1)` 是 dynarec 翻译块里的一个 native call。在这个上下文里做任何同步异常分发（guest signal frame、TF、host 信号）都会破坏 JIT 块的寄存器/执行状态：`emit_signal` 走 siglongjmp，TF 走解释器切换，host 信号被 box64 自己消费。**Wine 的 `trap_handler` 收不到带正确 guest 上下文的 TRCTRAP。**

**顺带坐实的正向结论**：
- 文件通道（Wine 写 `hwbp_watch.txt`、box64 读）**稳定可用**：`jit6` 1629 命中、`jit15` 2427、`jit16` 28679
- mmap 共享通道也打通：`jit12` 的 `seen=dr1=31f014`、`calls=1582 万`，证明 box64 能实时读到 Wine 写的 Dr1
- **`jit12` 的 `jithit=0`、`lastesp=10f5c0` 说明 post-push ESP 与 watch 地址不在同一区域** —— 即使投递问题解决，当前「比较 post-push ESP」的判据本身也不够（`hwbp_push_delta` 覆盖 `0x68/0x6A/0x9C/0x60/0xE8/0xFF`，我只插了 `0x50-0x57`）

**结论：整条 JIT 插桩路线到此终止**。不是参数没调好，是三个结构性障碍叠加：① JIT 块内不能同步投递异常；② 插桩 opcode 覆盖不全；③ Dr1 每次 arm 都变，通道与判据都要重做。继续投入需要重写 box64 的异常分发路径（在 dynarec epilog 而非 native call 里投递），工程量远超 19.8 s 的收益。

   **`addr` 与 `dr1` 逐字节相同**，`idx=2` 是代码 `return i+1`（Dr1 命中）。⇒ **perf 监视的地址完全正确，地址不是失败原因**。（顺带确认：页内其它地址 `addr=31ea04` 不命中、`idx=0`，误报判据也没问题。）
2. **信号有没有到 ntdll**：M3c 的日志只有 `TRAP sig=5 code=128`（int3），**没有 `code=-4`（`SI_SIGIO`）**。需要专门打点确认「perf 命中 → SIGTRAP → `SI_SIGIO` 分支」这条链有没有走通。
3. **`cnt=1` 可能是「页故障顺带记录」而非纯 perf 命中**：标题期的 `cnt=1` 是在**页保护开着**的情况下测的 —— 访问先触发页故障、ntdll 处理，perf 可能只是顺带记了一笔。M3c 关掉页保护后纯 perf 反而 `cnt=0`，这个矛盾说明「纯 perf 是否真能独立触发」还没证明。**下一轮要在无页保护、地址确定被访问的场景里验证**（例如对游戏栈的低端地址 `0x7fceffe000` 试，或找一个确定在写的堆地址）。

**已排除的测试流程 bug**：曾用 `rm` 删 ring 文件再测，导致 helper 的 mmap 指向旧 inode、读不到新 entry（表现为 helper 只收到 1 次 ARM）。正确做法是**重启 helper**（它自己 `ftruncate` 重建）。
