# 组件优化研究：流畅度 + 画地图/攻击范围速度（2026-11-06 晚）

> 任务：读模拟器源码，找出还能优化哪些组件，加强游戏流畅度、加快画地图/攻击/移动范围。
> 方法：4 路并行精读 —— ① Winlator 8.0 Java 管线（jadx `out8` + 当前 smali `candF`）
> ② 原生 C（`w8src/cpp/winlator`）③ Wine 9.2 GDI 全路径（`/root/wine0905`）④ box64 dynarec（0.3.8 源码对照）。
> 所有结论均有 文件:行号 依据；测量锚点沿用《2026-11-06_渲染与卡顿攻坚日志.md》。

---

## 0. 结论先行

1. **画范围/画地图的速度瓶颈在游戏进程侧的 Wine GDI 像素循环**（wow64 下 100% 跑在 64 位
   `win32u.so`，被 box64 翻译执行）。测量锚点：画范围 0.23 s 窗口内游戏进程烧 0.42 s CPU
   （≈183% 单核），App 侧 X 光栅只有 0.06 s —— **App 侧组件再怎么优化，上限就是那 0.06 s**。
2. **唯一量级可观的杠杆 = 让 Wine 热循环落回原生 ARM**。box64 对**显式 `memcpy/memset` 调用**
   直调原生 NEON 实现（bridge 0xCC + isSimpleWrapper → `call_n`），对**内联 `rep stos`** 只有
   8 字节/迭代的翻译循环，对逐像素 C 循环逐条翻译。把 win32u 的 PatBlt/ROP 循环改写成调 libc，
   是收益最大、风险最低的方向（不碰任何异常语义）。
3. **每帧固定开销有个隐形大头**：`dc->dirty` 时每次 blit 都附带一次 wineserver 往返 +
   `XSetClipRectangles` + dibdrv 重绑 —— 这就是 388 次/秒 SetClipRectangles 的来源。App 的 X
   服务器对 opcode 59 是直接丢弃的（`client.skipRequest()`），所以这个成本全在客户端侧，可缓存消掉。
4. App 侧只值得做三件便宜事：**wineserver 钉大核**（现在混跑 0-7 核）、xconnector 的 JNI
   方法缓存、`fromBitmap` 卫生修改；`copyAreaOp` 要先实测确认是否在热路径。
5. SHM 上传路径已经是零拷贝 + 50ms 批量合并（92 次/秒与实测吻合）→ **上传/X 服务器侧已最优**，
   16bpp 管线、脏矩形上传等老话题继续维持「不做」。

## 2. 一条 blit 的完整旅程（源码地图，全部 file:line）

```

  └ gdi32 PE: dc.c:1922 BitBlt→NtGdiBitBlt(dc.c:1934)；dc.c:1907 PatBlt(:1916)
     └ 32 位 win32u.dll 全是 -syscall 桩 (win32u.spec:107+, main.c:95/694)     ← 32位侧无像素代码
        └ ★恰好 1 次 wow64 syscall 穿越 (win32syscalls.h:12/415;
           64 位 dispatcher signal_x86_64.c:3377 保存全 GPR+xsave)
           └ 64 位 win32u.so: bitblt.c:576 NtGdiBitBlt→:584→:641-644 physdev
              └ dibdrv 函数表 dibdrv/dc.c:676 (pPatBlt) /:705 (pStretchBlt)
                 ├ execute_rop: dibdrv/bitblt.c:741-806 (BITBLT_Opcodes[256] :49)
                 ├ copy_rect 分发: bitblt.c:473-556
                 ├ 脏区累积: dibdrv/dc.c:305-323 add_clipped_bounds → surface bounds(单大矩形)
                 ├ 每次 blit 前的 update_dc: win32u/bitblt.c:545(PatBlt)/:591(BitBlt)
                 │   dc->dirty ⇒ dce.c:459 update_visible_region =
                 │   ★wineserver get_visible_region 往返 + XSetClipRectangles + dibdrv 重绑(dc.c:763)
                 └ 像素循环(全部在 win32u.so, box64 翻译执行):
                     SRCCOPY   → copy_rect_32 primitives.c:1399-1401 每行 memmove → ★原生 ARM
                     SRCAND 等 → do_rop_codes_line_16 primitives.c:179-182(16bpp 逐像素)
                                 copy_rect_bits_32 primitives.c:1341-1359(32bpp 逐 DWORD=逐像素)
                     PATCOPY   → memset_32/16 primitives.c:247-263 ★x86_64 内联 rep stos(box64 只 8B/迭代)
                     DSTINVERT → solid_rects_16/32 primitives.c:429-433 逐像素 NOT
  └ flush（一次 blit 不上传）: FLUSH_PERIOD 50ms(dibdrv/dc.c:726,750-758) + 消息空闲(dce.c:397-413)
     └ x11drv_surface_flush winex11.drv/bitblt.c:1906-1968
        32bpp 无字节序转换时 surface->bits == image->data ★SHM 零拷贝(bitblt.c:2059-2069)
        → 一次 XShmPutImage(bitblt.c:1950) 传整个 bounds → XFlush(:1964)
     └ X 服务器(App): opcode 59 → XClientRequestHandler.java:711-713 ★直接 skipRequest（无成本）
        MIT-SHM PutImage → MITSHMExtension.java:79-110 → Drawable.drawImage(原生 copyArea 直写 buffer)
        → texture.setNeedsUpdate → onUpdateWindowContent → requestRender(GLRenderer.java:170-172)
        → GLThread: Texture.updateFromDrawable glTexSubImage2D 整块 GL_BGRA 直传(Texture.java:118-131)
```

三个关键架构事实：
1. **像素循环 100% 在 64 位 unix 侧**（wow64 构建，gdi32 PE 只是桩）→ 全部被 box64 翻译。
2. **上传已是零拷贝 + 批量**（bounds 合并成一个大矩形，50ms/消息空闲 flush）→ 92 次/秒即实测值，
   X/上传侧没有水可挤。
3. **SetClipRectangles 388/s 成本在客户端不在服务器**（服务器直接丢弃），来源是每帧 GetDC 后
   第一笔 GDI 的 `update_dc`（`dc->dirty` 置位 → `set_dc_dce` dc.c:1184）触发的全套重建。

## 3. 把画范围的 0.42 s 游戏侧 CPU 分解（推断，待 A0 实测确认）

| 模式 | 游戏行为 | 落到哪段代码 | box64 下的状态 |
|---|---|---|---|
| A 范围/迷雾/选择框 | DSTINVERT/GXxor 类无源 ROP 小块高频 | solid_rects_32 逐像素 NOT（primitives.c:429-433 系） | 慢（翻译逐像素） |
| B 单位/精灵贴图 | SRCAND+SRCPAINT 掩膜 blit 或 SRCCOPY | SRCCOPY=memmove（快）；掩膜=do_rop_codes_32 逐 DWORD（慢） | 一半快一半慢 |
| C 地面/背景块填充 | PATCOPY 实心/图案刷 | memset_32（内联 rep stos）/pattern_rects_32 | 慢（非原生 memset） |
| D 每帧固定开销 | GetDC 后首笔 GDI | wineserver 往返 + XSetClipRectangles + dibdrv 重绑 | wineserver 混跑 0-7 核 |
| E 翻译税 | 所有短基本块 + call/ret 密集 C 代码 | 出块→jumptable 查址/LinkNext（dynablock.c:322-414）+ RET 前 READFLAGS | 结构性，靠 BIGBLOCK/CALLRET 缓解 |

待实测：游戏真实 ROP/尺寸直方图。现成通道 `WINEDEBUG=+bitblt`（win32u/bitblt.c:36 声明，
:568 PatBlt / :599 StretchBlt 的 TRACE 含 ROP+尺寸；+dib 通道 graphics.c:1187 打 PatBlt）。
注意两点：App 会先放 `WINEDEBUG=-all`，但容器 envVars 的 putAll 在其后可覆盖
（XServerDisplayActivity.java:486-505）；游戏进程 stderr 默认 → /dev/null，要同时开
`WINE_HWBP_LOG=1` 让 ntdll 构造器把 stderr 落到 `hwbp.log`（顺带拿到 +bitblt 的输出）。

## 4. 优化项清单

### A 层：重编 win32u（动 `/root/wine0905`，收益大头）

| # | 改动 | 位置 | 改法 | 预期 | 风险 |
|---|---|---|---|---|---|
| A0 | **先实测 ROP/尺寸直方图** | 运行时 | `WINEDEBUG=+bitblt` + `WINE_HWBP_LOG=1`，进战斗/画范围各采 30s，PC 端解析 | 决定 A1-A3 优先级与预期上限 | 无 |
| A1 | memset_32/16 改走 libc | primitives.c:247-263 | 栈上 64B tile memset 一次 + 每行 memcpy（或宽指针展开）；PATCOPY/BLACKNESS/WHITENESS 全受益 | 翻译 rep stos(8B/迭代) → 原生 NEON memset，**3-10 倍** | 低 |
| A2 | 32bpp 无源 ROP 加宽 | primitives.c:429-433 系（solid_rects_32/DSTINVERT） | uint64 两像素一迭代 + 行尾奇偶处理 | 2-3 倍 | 低 |
| A3 | 带源 ROP 加宽 | do_rop_codes_line_32 / copy_rect_bits_32（primitives.c:1341-1359） | and/xor 掩码预复制成 uint64，两像素一迭代；行首尾单独处理 | 掩膜贴图（SRCAND/SRCPAINT）2-3 倍 | 中（对齐/行尾） |
| A4 | mem↔mem 直通 | dibdrv/bitblt.c:1407-1416（dibdrv_StretchBlt 兜底进 nulldrv GetImage→PutImage 往返） | dst 为 dibdrv 且源同格式非重叠时直接 copy_rect，免 BITMAPINFO 构造与握手 | 壳/游戏内部 DIB 搬运受益 | 低-中 |
| A5 | update_dc 缓存跳过 | dce.c:459-530 + win32u/clipping.c:207-229 | 可见区/surface 未变时跳过 wineserver get_visible_region 往返、XSetClipRectangles、dibdrv 重绑（缓存键=窗口 geometry/region 版本，变动时失效） | 消 388/s X 请求 + 每 blit 重绑 → 画范围瞬时响应改善 | 中（失效逻辑要准） |
| A6 | 单文件 -O3 | dlls/win32u 的 primitives.c/bitblt.c | `-O3` 循环自动向量化成 SSE2 宽 load/store（box64 SSE2→NEON 1:1，翻译质量好） | 与 A1-A3 叠加 | 低 |

## 6. 实施顺序建议（两轮，每步有验收）

**第一轮（不动 Wine，1 次设备来回）**

4. B1：wineserver 钉大核（先用 adb 手动 taskset 验证收益，有效再固化）。

0.306s/0.345s）+ 滚动 6 秒负载（基线 2.17s/2.54s）+ 战斗 30s p90（基线 49.9ms）。

**第二轮（重编 win32u）**
1. 按 A0 直方图选 A1/A2/A3 中命中的，连同 A6 一批编入。
2. A4/A5 视第一轮剩余 profile 决定。
3. 部署 = 换 win32u 两半 + .orig 备份，回滚同 ntdll 模式。

判定标准沿用项目惯例：单次波动 ±2s / 帧间隔看 p90 与 >80ms 占比，只认 >3s 或比例级差异。

## 8. A0 实测结果（2026-11-06 晚已完成 ★）

方法：手机容器 `WINEDEBUG=+bitblt` + `WINE_HWBP_LOG=1`，launch → 标题 65.5s → 读档汜水关 →
30s 采样（12 次地图点击）→ hwbp.log 785MB → gzip 4.8MB 拉回 → 解析（`unpack_tools/a0_rop_trace.py`
+ `a0_analyze.py`，原始 gz 在 `unpack_tools/a0_trace/hwbp_a0.log.gz`）。

### 8.1 ROP 直方图（26,649 次 blit / 26 万行日志，含解包+菜单+战斗）

| ROP | 次数 | 占比 | 像素 | 走哪段代码 | 结论 |
|---|---|---|---|---|---|
| SRCCOPY `cc0020` | 26,649 | 83.3% | 62.4M | copy_rect_32 每行 memmove → 原生 ARM | 已快，不动 |
| PATCOPY `f00021` | 3,482 | 10.9% | 2.5M | memset_32 内联 rep stos（box64 慢路径） | **A1 确认** |
| DSa `220326` | 518 | 1.6% | 0.46M | do_rop_codes 逐像素 | **A3 确认** |
| SRCPAINT `ee0086` | 456 | 1.4% | 0.47M | 同上 | **A3 确认** |
| SRCAND `8800c6` | 380 | 1.2% | 0.43M | 同上 | **A3 确认** |
| BLACKNESS | 260 | 0.8% | 0.07M | memset | 无碍 |
| `e20746` | 152 | 0.5% | 0.08M | 逐像素 rop3 | 顺手 |
| `1100a6` | 76 | 0.2% | 0.04M | 逐像素 rop3 | 顺手 |
| **DSTINVERT `550009`** | **0** | — | — | — | **A2 取消**（游戏根本不用） |

尺寸分布：**1x3 像素 ×18,973 次**（每笔都付 update_dc/wineserver 固定开销 → A5 价值坐实）、
48x48 ×4,030、16x16 ×1,061、96x14 ×980、32x32 ×915。

### 8.2 上传侧新发现

flush 3,477 次共 **24.3 亿像素**，其中 **93% 是 992x736 整窗口上传**——Wine 把所有脏区合并成
一个大 bounds 矩形，每次 flush 都重传整个窗口。X 服务器侧是 SHM 零拷贝+整块纹理上传，之前实测
减半上传无收益（日志 §2.5），维持不动，仅记录。

### 8.3 实验中的重大发现：`WINEDEBUG=+dib` 是启动杀手 ★

手机容器 env 里遗留着上次调试的 `WINEDEBUG=+dib`（stderr→/dev/null 仍要逐条格式化）：
**连续 3 次启动失败**（hwbp arms 停在 960/1152，健康值 1536-1600，t≈27-32s 断气）；
换 `WINEDEBUG=-all` 后一次成功（82.7s 出标题）。结论：dib 通道的日志开销会卡死 VProtect 壳的
反调试时序，**生产环境必须 `-all`**（已固化到手机容器，快照见
`device_backup/phone_container_20261106_prod.txt`；带 +dib 的旧快照留档
`phone_container_20261106_a0.json`）。这解释了部分「启动偶发黑屏 50%」的历史现象——
至少在本轮，黑屏与 env 直接相关而非纯随机。

### 8.4 B1 钉核结论（做了，没做成，原因明确）

adb shell（uid 2000）、`run-as com.winlatcn`、`su` 三条路给 wineserver `taskset` 全被
Permission denied 挡死（SELinux shell→app uid；无 root）。可行路径二选一，都挪到第二轮：
1. App 侧 smali 补丁：容器起来后 `Runtime.exec(taskset -p f0 $(pidof wineserver))`
   ——App 对**同 uid** 的 wineserver 是否放行待验证（自己线程已验证可行）；
2. Wine 侧补丁：`server/main.c` 里对自身 `sched_setaffinity`（与 win32u 同批重编）。

### 8.5 C2 hotpage 排查结论

box64 0.3.8 对 HotPage 机制**没有任何日志输出**（custommem.c/dynablock.c 无 printf_log），
无法用日志排查。要么给 box64 加计数器补丁（与第二轮 box64 改动同批），要么搁置。

## 9. 第二轮实测结论（2026-11-07 凌晨）

1. **重编 win32u 的两个硬前提**（缺一即崩，且都发生在解包后的 GUI 初始化）：
   - `--with-freetype`：freetype-less 构建建字体即崩；原版二进制的指纹 = UND 含
     dlopen/dlsym/dlerror/dlclose + open/mmap/__fxstat/close + wine_nt_to_unix_file_name；
     运行时字体库走 imagefs 的 ARM64 libfreetype（box64 原生桥接）。
   - `-DNDEBUG`：原版无 `__assert_fail`；树构建的 `assert(!IsRectEmpty(rc))` 会 abort。
2. **A1 memset→libc 同协议 A/B 判零收益**（r110 0.447 vs r109f 0.442 s/次，10/10 有效开关）：
   画范围 CPU 大头 = SRCCOPY 83%（已原生 memmove）+ 游戏逻辑 + box64 翻译税，与 A0 直方图自洽。
3. **App/组件侧优化空间已尽**：A3/A6 外推判负；A5/B1 为剩余项但预期 ~5% 以下。
4. 壳对时序极度敏感：**任何 wine 日志通道（+loaddll/+dib/+bitblt）都会触发反调试**（faults 暴涨），
   Wine 侧诊断只能靠 A/B 二分 + 二进制取证（symdiff/sysnum_diff）。
5. 手机最终状态：win32u=r109f，env=生产配置，回滚一条命令（`deploy_win32u.py orig`）。
