# box64 重构评估：32 位 vs 信号路径（2026-11-12）

> 用户提出「把 box64 重构成 32 位」。本文先验证这个前提，再用计时数据找出真正值得重构的地方。
> 结论：**32 位重构不成立**（三个硬事实）；但计时发现 **19.8 s 的 100% 是「调用 guest handler」**，这是唯一还有理论空间的位置，且**「让 box64 拦截误报」已被本轮实验否掉**。

---

## 1. 「重构成 32 位」：三个硬事实否掉前提

| 事实 | 证据 |
|---|---|
| **box64 不加载 32 位 ELF** | `src/elfs/elfloader.c` 里 `grep ELFCLASS32` 为空；`CMakeLists.txt` 无 `BOX32` 选项；实测 `box64 cp32` 报 `Error: Reading elf header of .../cp32, Try to launch natively instead` |
| **Wine 是 64 位（new wow64）** | 容器内只有 `opt/wine/bin/wine`（无 `wine64`），库在 `opt/wine/lib/wine/x86_64-unix/` |
| **32 位代码只是「64 位进程内的代码段」** | 走 `is32bits` 分支（dynarec 里 102 处），不是独立 ELF 加载路径 |

⇒ 「纯 32 位」意味着：**换 32 位 Wine（需退回 Wine 9，Wine 10 已放弃 32 位 prefix）+ 移植 box86 + 把约 2000 行 `hwbp_*` 补丁重写到 box86 的 `signal_i386.c`**。

**收益上限**：只影响纯 VM 段 7.1 s 的 20~40% = **1.4~2.8 s**；页故障 19.8 s 一分不动。
**风险**：VProtect 反调试依赖 box64 的特定信号时序，重写后大概率跑不起来。
**判定：不做。**

补充事实（对以后有用）：设备**支持 32 位用户态**（`ro.product.cpu.abilist` 含 `armeabi-v7a`，`/system/lib` 与 `/system/bin/linker` 都在），所以 box86 不是「设备不支持」，而是「工程量/风险不划算」。

---

## 2. 真正值得看的地方：19.8 s 的 100% 是 `RunFunctionHandler`

### 2.1 原生基线（app 域，无 proot / 无 box64）

`tools/cost_probe.c`（aarch64 static）：

```
C getpid            : 0.29 us/call
B mprotect 4KB pair : 0.75 us/pair  (0.37 us/call)
A SIGSEGV trip      : 0.99 us/trip
```

⇒ `mprotect` 与内核信号投递合计 **< 2 µs**，而游戏内一次页故障 **≈ 450 µs**。**99.5% 不在内核。**

### 2.2 Wine 侧只占 10.9 µs

在 `hwbp_handle_rw_fault` 内加 `clock_gettime`（`fix110b_tprof`）：

```
wns=10925 wcalls=44090      => Wine 侧每次 10.9 µs（2.4%）
```

### 2.3 **box64 的 `RunFunctionHandler` 占 247.8 µs**

在 box64 的 `my_sigactionhandler_oldcode` 里分段计时（干净 0.3.0 源码，`b64prof`）：

```
prof calls=87040  prep_avg=1217  run_avg=247778  fin_avg=98
```

| 分段 | 内容 | 每次耗时 |
|---|---|---|
| `prep` | 互斥锁 + `thread_get_emu` + 构造 x64 sigframe + 切栈 | **1.2 µs** |
| **`run`** | **`RunFunctionHandler`（执行 guest handler = Wine 的 `trap_handler`）** | **247.8 µs** |
| `fin` | 恢复寄存器 + 解锁 | 0.1 µs |

- `calls=87040` = `faults 44090 + steps 42990`（SEGV + TF 单步各一次），完全吻合；
- **87040 × 247.8 µs ≈ 21.6 s**，正好对上 19.8 s（后者按拟合 β 折算，这里是直接累加）。

⇒ **19.8 s 的本质：每次页故障要把一个 host 信号转发成 guest 异常，而「进入 guest handler」单次 247.8 µs。**

### 2.4 为什么 `RunFunctionHandler` 这么贵（未逐行坐实）

它要：
1. 把 host `ucontext` 转成 `x64_ucontext_t`（20+ 寄存器逐一拷贝）；
2. 在 guest 栈上搭 832 字节的 signal frame；
3. **切换到 guest 栈**（`R_RSP = frame`）；
4. 调用 guest handler（x86 代码）—— 若目标块未 JIT 过，还要**现场翻译**；
5. handler 里再调 `hwbp_*`（10.9 µs）+ `mprotect`（0.4 µs）；
6. 回来后检查 `memcmp` 决定是否回写寄存器。

**247.8 µs 里，Wine 自己的逻辑只占 10.9 µs**，其余 ~237 µs 是「进出 guest 上下文 + 执行 handler 代码」的开销。

## 3. 尝试：「让 box64 自己处理误报，不转发给 guest」——**前提不成立**

思路：误报（43,706 次）不需要 #DB，理论上 box64 可以在 host 侧直接「解锁 + 复保护」，只把真命中（400 次）转发给 Wine。若成立可省 21 s。

**验证**：在 box64 的 `my_sigactionhandler_oldcode` 里统计「`sig == SIGSEGV` 且 `si_addr` 落在 `0x31f000` 页」的次数。

```
prof calls=87040 ... segv31f=68
samples: si_addr=31f014 low32=31f014
faults=44090
```

**`segv31f=68` vs `faults=44090`** —— box64 的 SIGSEGV handler 只见到 **68 次**落在监视页，而 Wine 统计到 44,090 次。

样本地址是 `0x31f014`（无高位偏移），说明不是地址比较写错，而是**这些信号根本没走到 box64 的 handler**。

### 未坐实的解释（下一步要查的）

1. **Wine 在 host 层自己注册了 SIGSEGV handler**，大部分页故障由它直接处理，box64 只是「在它下面」；
2. 那 `calls=87040` 的 `RunFunctionHandler` 里，SIGSEGV 只占 68 次，其余 86,972 次是**别的信号**（SIGTRAP 43,006 及其他）——**这条与 `calls ≈ faults + steps` 的吻合是巧合**；
3. 也可能 `b64p_segv` 的计数被 `-O3` 优化掉了（概率低，因为同时有文件写副作用）。

⇒ **「box64 侧拦截」这条路在验证阶段就被否掉**，不能作为方案。

## 4. 本轮净结论

| 方向 | 结论 | 依据 |
|---|---|---|
| 重构成 32 位 | ❌ 不做 | box64 不加载 32 位 ELF + Wine 是 64 位 + 收益上限 2.8 s |
| 让 box64 接管误报 | ❌ 前提不成立 | `segv31f=68` vs `faults=44090` |
| 优化 `RunFunctionHandler` | 🔬 **唯一剩下的方向** | 247.8 µs/次，87,040 次 |

### 若继续「优化 `RunFunctionHandler`」，可查的三点

| 编号 | 假设 | 怎么验证 |
|---|---|---|
| R1 | guest handler 每次都在**解释执行**（未 JIT/未缓存） | 在 `RunFunctionHandler` 里打印「是否命中已翻译块」；或对比 `BOX64_DYNAREC_BIGBLOCK` 变化对 `run_avg` 的影响 |
| R2 | 构造 832 字节 signal frame + 切栈占大头 | 已在 `prep` 里（1.2 µs），**排除** |
| R3 | `memcmp(sigcontext, &sigcontext_copy, sizeof(x64_ucontext_t))` 每次比较 300+ 字节 | 打点计时；若占比高，可改成「只在 guest 写了标记时比较」 |

**R1 最可疑**：247.8 µs 相当于执行几百到上千条 x86 指令的时间。Wine 的 `trap_handler` 只有几十条指令，除非**它在解释器里跑**，或者**每次都在重新翻译**。

## 6. 实测：让信号 handler 走 JIT（三档，全部不可用）

### 6.1 根因确认

`RunFunctionHandler()` 里有：
```c
#ifndef USE_CUSTOM_MEM
    dynarec = 0;   // 所有信号 handler 强制解释执行
#endif
```
而调用处本来写了 `if (sig != SIGSEGV && ...) dynarec = 1;` —— **被这一行抹掉了**。

### 6.2 分段计时（干净 0.3.0 + 打点）

```
segv_n=43898  segv_run=465013ns   -> SIGSEGV 465 us/次（解释器）
trap_n=43142  trap_run=22768ns    -> SIGTRAP  22.8 us/次（JIT 放行后）
```

⇒ **`247.8 µs` 是平均值，被 SEGV 的 465 µs 拉高。真正的大头是 SIGSEGV。**

### 6.3 三档 A/B

| 档 | 改动 | t（解包） | 稳定性 |
|---|---|---|---|
| 生产基线 | 无 | 29.7 / 30.0 / 30.0 | 3/3 成功 |
| 只 SIGTRAP 走 JIT | `allow=(sig==SIGTRAP)` | 30.1 | 1/1 成功，**无收益** |
| 全信号走 JIT | `allow=1` | **28.0 / 28.1** | **3/5 成功（2 次卡死）** |
| 栈区过滤 | 只在 `si_addr ∈ [0x30000000,0x40000000)` 时允许 | 29.9 / 29.2 | 2/3 成功，**无收益** |

**关键判读**：
- 「全信号走 JIT」省 1.7 s，但卡死率 40%（`arms` 停在 576/1088）；
- 「栈区过滤」本想保住收益又避开 malloc 重入，结果收益消失（29.2~29.9）——**说明那 1.7 s 恰恰来自「在 malloc 期间也走 JIT」这种危险路径**；
- SEGV 单次只从 465 µs 降到 425 µs（−9%），其余 450 µs **不在指令执行上**，而在 Wine 的异常分发逻辑里（`hwbp_handle_rw_fault` 只占 10.9 µs）。

⇒ **JIT 开关不是杠杆。** 即使全开，也只值 1.7 s，且用稳定性换。

### 6.4 关于「卡死簇」的运维结论（本轮踩到）

连续 5 次卡死（`arms` 停在 128/256/576/1088/1280）后确认：
- **不是改动导致**（生产二进制同样卡）；
- **不是过热**（36.8 °C）、**不是内存**（6.5 GB available）；
- **真正原因**：`am force-stop` 杀不掉 proot 子进程，残留 `libtinyproot.so` + `winedevice.exe` 叠加。
- **有效恢复步骤**（本轮验证）：`am force-stop com.winlatcn` → 等 3 s → `rm -rf files/imagefs/tmp/*` → 重跑。一次即恢复（44.9 s / 1600 / 400）。


## 7. 最终结论

| 问题 | 答案 | 证据 |
|---|---|---|
| 能重构成 32 位吗 | ❌ 不做 | box64 不加载 32 位 ELF + Wine 是 64 位 + 收益上限 2.8 s |
| 19.8 s 卡在哪 | **SIGSEGV handler 单次 465 µs** | `segv_run=465013ns × 43898` |
| 其中 Wine 逻辑占多少 | **10.9 µs（2.3%）** | `wns=10925` |
| 剩下 450 µs 是什么 | Wine 异常分发 + 进出 guest 上下文 | JIT 只省 40 µs（465→425），说明瓶颈是**逻辑不是执行** |
| 把信号 handler 改走 JIT 有用吗 | ⚠️ 省 1.7 s，但 40% 卡死 | 28.0/28.1 vs 基线 29.7~30.0，3/5 成功 |
| 有安全的折中吗 | ❌ 加地址过滤后收益归零 | 29.9/29.2 |
| 19.8 s 能消除吗 | **不能** | 四条替代通道全判死 + JIT 无杠杆 |

**唯一真正可用的产出**（本轮意外收获）：

**卡死簇的正确恢复步骤** —— 之前一直以为要「重试到第三次」，实际是 `am force-stop` 没杀掉 proot 子进程：
```
am force-stop com.winlatcn
等 3 s
rm -rf files/imagefs/tmp/*
```
一次即恢复（44.9 s / arms=1600 / hits=400），不用再赌第三次。

**启动时间维持 44.9 s（生产态）**，19.8 s 到此为止。
