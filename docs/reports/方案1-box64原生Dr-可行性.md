# 方案 1 可行性研究：在 box64 里原生实现 x86 Dr0–Dr3 数据断点

日期：2026-11-02　结论：**技术上可行，但投入产出比不划算，建议不做**（除非把"启动时间"当第一优先级）。

---

## 1. 为什么要考虑它

当前实现（fix99）在 Wine 的 ntdll 里做：页保护 → 页故障 → 切页 → 置 guest TF 单步 → 陷阱 → 复保护。
每次被监视页上的**任意**访问都要走两轮信号 + 两次 mprotect。解包期大约 780 个 VM 步，每步上百次访问，
即几十万次异常往返。整包启动 ≈ 50 s，其中相当一部分花在这条路径上。

方案 1 的思路：让 box64（真正执行 guest 指令的那个 JIT）自己识别被监视的访问，直接抛 #DB，
省掉信号往返和 Wine 的异常分发。

## 2. box64 现状（0.3.0 源码实查）

- **完全没有 Dr 支持**：`grep -rn "dr7\|hwbreak" src/` 只命中 `wrappedlibc.c` 里一条 "clean up DR7" 注释。
  `x64emu_t` 里也没有 Dr0–Dr7 字段。
- 32 位（wow64）代码是走 arm64 dynarec 的（`is32bits` 在 `dynarec_arm64_*.c` 里普遍被判断）。
- **有利条件**：32 位访存的地址计算有统一收口宏 **`GETED(D)`**（`dynarec_arm64_helper.h`，109 处调用），
  算完地址就在 `ed`/`x1` 里，插检查点的位置是明确的。

## 3. 要做的事（按难度排序）

1. **状态**：`x64emu_t` 加 `dr[4] / dr6 / dr7`。
2. **Wine → box64 的通道**：Dr 值是壳通过 `NtSetContextThread` 写进来、由 Wine 收到的（现在就是我们在 Wine 里拦）。
   要让 box64 用上，需要一条通道把 Dr 值传下去（导出符号 / 共享内存 / 复用 wow64 CPU area）。**这是最不确定的一环**。
3. **检查点**：在 `GETED` 之后比较 `ed` ∈ [Dr_i, Dr_i+len)，命中就记一笔。
4. **投递时机**：硬件数据断点是**指令执行完**才报。GETED 在访问之前 ⇒ 不能在 GETED 处直接抛，
   得在**这条指令结束时**抛 #DB 并置 Dr6。也就是要能在每条指令后切块退出——只能在主分派循环里插检查。
5. **push/call 语义**：我们已经在 Wine 侧踩过（box64 在存储故障时 RSP 已减好），这条在新实现里同样要处理。

## 4. 性能账（这是不建议做的主因）

- 若在**每条 x86 指令**后都插"armed? hit?"检查：静态就是每条指令多 4 条 ARM 指令，
  **常态**（没 armed 时）也要付这笔钱，估计整机慢 15~25%。
- 想避免常态开销，只能"arm 时让相关 dynablock 失效并重编译"——但解包期 arm/disarm 约 780 次，
  每次全量重编译的代价远大于收益。
- **折中方案**：只给 **packer 代码区（0x58xxxx 段）** 的块编译检查代码。其余代码零开销。
  这个方向可行，但需要改 dynablock 生成逻辑 + 区域判定，工程量仍不小。

## 5. 关键判断：收益只落在"启动"，不在"游戏流畅度"

实测：进入游戏后（标题/战场）watch 是**空闲**的——游戏待机 CPU ~5%，
若被监视栈页还在 armed 状态，每次栈访问都会故障，不可能只有 5%。
也就是说壳只在解包期使用这个机制。

所以方案 1 最多把 **50 s 启动**里的异常往返压掉一部分（还要扣掉新的每指令检查开销），
**对"游戏里卡不卡"没有一点帮助**。

## 6. 建议

- 如果目标是"游戏更流畅"：方案 1 帮不上忙（瓶颈是 box64 翻译游戏逻辑/GDI 绘制，实测持续移动时游戏进程稳定吃 57~58% 单核）。
- 如果目标是"启动更快"：更便宜的路线是把 Wine 侧每次故障的两次 mprotect 合并、减少信号往返，
  预计能拿回几秒，工作量是方案 1 的十分之一。
- 真要做方案 1，建议按第 4 节的"只插 packer 代码区"来做，并准备好 dynarec 回归测试集
  （我们的 tests/ 里已有 tf3_test / stkfault 等探针可复用）。

## 7. 附：如果真要动手，第一个里程碑

不碰 Wine，先在 box64 里加一个**可运行时开关的** `watch` 机制：
当 `BOX64_WATCH=addr:len` 被设置时，只对 `0x580000–0x590000` 区间的块插检查并在命中时打日志，
用 `Ekd5.exe` 跑一遍，比对"命中地址序列"是否与 fix99 记录的 Dr1 命中序列一致。
一致 ⇒ 通道和时机都对了，再往下接 #DB 投递。

## 8. 补充（同日实测后修正结论）

在动手前先做了"最小优化 + 打点"（fix103），量出了解包期的真实事件量：

```
arms=1600  faults=44381  steps=43281  hits=400
```

- 一次启动 53 s，异常事件只有 4.4 万次；按每次 30~100 µs（信号往返 + mprotect + Wine 分发）估，
  这套补丁总共只贡献 **1.3~4.4 s**，即启动时间的 3%~8%。
- 剩下 ~45 s 是 box64 在正常执行壳的 VM 解密循环本身，与断点机制无关。

**因此方案 1 的天花板也就是几秒**（把 4 万次异常换成更便宜的检查路径），而不是原先估计的"能大幅缩短启动"。
叠加"要为每个 32 位指令/访存加检查、有 dynarec 回归风险"的成本，**结论：不值得做**。
