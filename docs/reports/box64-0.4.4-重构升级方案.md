# box64 0.3.0 → 0.4.4 升级重构方案（研究规划，2026-11-08）

> 本文是**规划**，不是结论。所有「已实证」项都给了文件/行号/md5；「待验证」项明确列出。
> 本轮未改任何二进制、未部署设备、未跑 boot。

---

## 0. 结论先行

1. **上一轮「0.4.4 终止」需要降级为「上一轮实验矩阵的结果」，不是路线判决。**
   实读源码与死亡现场后发现：box64 侧全修复版与 wine 侧全修复版**从未在同一次 boot 上组合过**。
2. **第一优先不是写重构代码，而是补全一个 2×2 组合矩阵**（现成 .so，0 新代码）。
   若交叉组合通关，升版路径可能只剩性能/回归验收；若不通，才进入源码级重构。
3. 存在一个此前没被控制的变量：r11x 系列与作者版 0.4.4 的**构建配置不同**（interpreter、体积均不同）。
   「只差一个变量」的 A/B 必须先补一个同配置无补丁对照版，否则结论仍然说不清哪处生效。
4. 收益预期（**未实测**）：0.4.4 全代码 10–30% 加速（日志 §20.1 的估计）；风险是 VProtect 壳对时序极敏感、
   调试日志本身会改变结果、连续失败会触发卡死簇。

## 3. 分阶段计划（单变量 / 可回滚 / 有验收）

### Phase 0：实验台固化（先做，0.5 天）

1. **验收标尺改为「第一分歧点」**，不再用「能不能出标题」当判据：
   - `unpack_tools/seq_align.py` 对齐 sim 事件序列（0.3.0 健康 27551 事件 vs 0.4.4 死亡 39 事件，§29）；
   - `hwbp_stats.txt` 四元组 `arms / faults / steps / hits`，**hits≈400 才是硬指标**；
   - 每轮 boot 单独存 `a0_trace/<组合名>_*.log` + 屏幕截图。
2. **补同配置对照二进制**：从 `/root/box64-0.4.4ntf` 反向还原 3 处补丁 → 同 CMake 配置编 `base_no_patch`，
   保证「base vs r112d」只差补丁（不差构建配置/interpreter）。
3. **固定量**：设备生产 env（`WINEDEBUG=-all`，零日志通道）、游戏 v2.20、容器、ntdll/box64 md5 打印、
   `set_mouse_drag.py true`（自动化前置，完事改回 false）。
4. **运维铁律**（血泪）：卡死簇 → `adb reboot` 复位，不在卡死态下结论；改源码后必须 `rm -rf build`
   全新配置（`copytree` 保留 mtime 会让增量 make 假成功，§22.3）；任何 `WINEDEBUG=+*` / `DYNAREC_LOG`
   都会改变壳时序，只用于取证、不用于验收。

### Phase 1：组合矩阵（P0，每格 1 boot ≈ 4 分钟）

| 格 | box64 | ntdll | 状态 / 目的 |
|---|---|---|---|
| A | 作者版 `a7360b1e` | fix110b | 已知：早死（§25/§31） |
| B | 作者版 | fix110c | 已知：解包 arms=1600 / hits=25（§32） |
| C | 作者版 | fix110d | 已知：解包但 faults 234K / hits=25（§32） |
| D | **r112d** `18b1f670` | fix110b | 已知：镜像视图堵死，NTCONT err=14（`r112d_death`） |
| H | **base_no_patch**（同配置） | fix110c | **未测·校准**：换构建配置能否复现 B |
| **E** | **r112d** | **fix110c** | **未测·第一优先**（与 H 只差 box64 补丁；与 D 只差 ntdll） |
| **F** | **r112d** | **fix110d** | **未测·第二**（与 E 只差 ntdll） |
| G | r113 `d234aa57` | fix110c | 未测·隔离 r112d 的 SIGTRAP 项（与 E 只差一处补丁） |

验收（每格）：`arms=1600` **且** `hits≈400` → 到标题 → 游戏进程存活 ≥15 s。
- E 或 F 通关 → 跳到 Phase 4；
- E/F 仍 hits≈25 → 进 Phase 2；
- 全部更早死 → 用 `seq_align` 定位新第一分歧点，回 Phase 0。

### Phase 2：页保护共存（条件触发）

- 冲突点：`custommem.c` 的 `protectDB/unprotectDB` 用 `mprotect(prot&~PROT_WRITE)` 维护 SMC，
  hwbp 用 `mprotect(PROT_NONE/PROT_WRITEWATCH)` 维护监视页，两套位图互相覆盖。
- 候选（按改动量）：
  1. 给监视页打 `PROT_NEVERCLEAN` / `always_test`，让 protectDB 跳过——`custommem.c:2346` 已有
     mixed-page 分支，**可能是最小改动**；
  2. 把 hwbp 保护位并入 box64 `PROT_CUSTOM`（需 Wine→box64 通道，导出符号或共享内存）；
  3. hwbp 不再改宿主 prot，改用纯 SIGSEGV + 软件判定（改动最大）。
- 验收：hits 25→400，且 `tests/tf3_test` / `hwbp_test` 在 0.4.4 上与 0.3.0 语义一致。

### Phase 3：信号语义对齐（条件触发）

- 以 0.3.0 `src/libtools/signals.c:1515-1533` 为黄金参考，逐项对齐 `signal32.c` 的
  EIP/EFL/ERR/TRAPNO、RF+SS、`copyEmu2USignalCTXreg` 直回 dynarec 路径。
- 验收：`seq_align` 前 N 个事件与 0.3.0 完全一致，而不是「感觉能跑」。

### Phase 4：升版切换与验收

- 部署链：box64（r112d 或最终版）→ ntdll（fix110c/d）→ win32u r109g → wineserver r112b → prod env → v2.20；
  每步 md5 打印并与 `build/` 锚点比。
- 回滚：`deploy_box64_044.py rollback` → 原版 0.3.0；ntdll 回 `fix110b`；`set_env_phone.py prod`；
  `final_restore.py` 一键复原。
- 性能 A/B（同场景，>3 s / >5% 才认差异，沿用既有口径）：启动到标题、待机 fps/p90、
  自动战斗 fps/p90。0.3.0 基线：72.1 s / 44.3 fps p90 17.1 ms / 30.1 fps p90 33.3 ms。
- **若无实质收益则不切换**——0.4.4 的收益是估计值，r111 自编反而慢 44%（§19/§20.1）。

## 7. P0 实测结果（2026-11-08 13:1x）

### 7.1 实验台健康闸门

`p0_health_check.py`（不部署、纯生产态）：**HEALTHY**，51 s 解包完成，
`arms=1536 / hits=384 / faults=44090 / steps=42990`，进程存活。
⇒ 后续所有「早死」不是设备卡死簇，也不是误判（判据已放宽到「连续 3 次无进程且 >45 s」）。

### 7.2 比组合空洞更根本的问题：r11x 二进制的构建配置是错的

| 项 | 官方树 `/root/box64-0.4.4`（= 作者版 `a7360b1e`，能跑） | ntf 树（r112c/r113/r112d 全部出自这里，全早死） |
|---|---|---|
| `ARM64` / `ARM_DYNAREC` | `ON` / `ON` | `OFF` / `OFF` |
| `CMAKE_EXE_LINKER_FLAGS` | `-Wl,--dynamic-linker=/data/data/com.winlatcn/files/imagefs/lib/ld-linux-aarch64.so.1` | **空** → interpreter 回落 `/lib/ld-linux-aarch64.so.1` |
| `NOGIT` | `ON` | `OFF` |
| 产物大小 / interpreter | 31,915,488 B / imagefs 绝对路径 | 25,999,904 B / `/lib/…` |

⇒ 上一轮所有 r11x 实验用的二进制在 Winlator 容器里**根本起不来**；
日志 §22/§31 里「r113 更早卡死」「六层穷尽」等结论需要按此重审。
本轮已在**作者版配置**上重新编出补丁版（`abfd2032…`、`23b60c67…`），

### 7.4 结论（单变量、可复核）

1. **交叉组合没有通关**：`hits` 从未接近健康值 384/400。
2. **r112d（SIGTRAP 不可延迟）单独无收益**：E4 与 B 形态完全一致。
   ⇒ §33 「defer_signal 延迟 SIGTRAP → 精确 RIP 丢失」不是 `hits=25` 的可修根因（至少单独修无效）。
3. **r112c / r113 里有有害改动**：E3（六处补丁）比 E4（一处）更早死；
   与日志 §22.3「r113 改回落空穿透 → 更早卡死」一致。glitch 改动应弃用。
4. **hits=25 的真正根因仍未定位**：`analyze_dr.py` 已证明壳设了 Dr、监视页也产生 SEGV，
   问题在命中判定 / 单步链，方向仍是 §2 的 P1（PROT_DYNAREC 与 hwbp 页保护争同页）
   与 P2（signal32.c 的 32 位 sigcontext）。
5. **按 §4 止损条件收尾**：P0 六格 + 健康闸门均无 hits 改善 → **暂停 0.4.4 升版，维持 0.3.0 终态**。
   F/F3/G 未跑：ntf 配置已证伪，六补丁在作者版配置下已早死，继续跑无新增信息。

### 7.6 若未来重启 ②，第一件事

不是再叠补丁，而是**给 `hits=25` 做一次可重复的实证定位**：

## 9. TF 同步链实证与两次修复失败（2026-11-08 13:3x–13:4x）

### 9.1 只读探针（E6）坐实「Wine 清 TF 生效」

`build/box64_efl_probe.so`（`186d6af2`，作者版配置）在

| 项 | 数值 |
|---|---|
| sig 分布 | 10(126)、17(100)、**5 SIGTRAP(61)**、11 SIGSEGV(39) |

### 9.2 源码：0.4.4 独有的双层 `old_eflags` 恢复

| 层 | 位置 | 行为 |

`emu2mctx()` 初始化 `sigcontext` 的 EFL 为 `emu->eflags | RF`，`mctx2emu()` 会读回 EFL ——
两版都有，不是差异点；差异在 0.4.4 新增的双层 `old_eflags` 恢复。

## 10. 源码终审：TF 回到 guest 的完整路径（2026-11-08 13:4x，纯读源码）

### 10.1 已确认的事实（全部有 file:line）

| # | 事实 | 位置 |
|---|---|---|
| 1 | guest EFLAGS 的权威副本是 `emu->eflags`：`#define ACCESS_FLAG(F) emu->eflags.f._##F` | `src/include/regs.h:392` |
| 2 | 主循环用 `ACCESS_FLAG(F_TF)` 决定是否走解释器单步 | `dynarec/dynarec.c:278`（0.4.4）、`dynarec.c:186`（0.3.0） |
| 3 | 宿主 ARM64 `ucontext_t` 把 guest flags 固定在 `regs[26]`（`xFlags`） | `dynarec/arm64/arm64_mapping.h:57` `#define xFlags 26`；`include/sigtools.h:10` `CONTEXT_REG(P,X)=(P)->uc_mcontext.regs[X]` |
| 4 | 把 emu EFLAGS 写回宿主槽的**唯一**代码：`CONTEXT_REG(p, xFlags) = emu->eflags.x64;` | `libtools/sigtools.c:854`（`copyEmu2USignalCTXreg`） |
| 5 | 该函数在 0.4.4 只被 3 处调用，全是 dynarec 特殊分支 | `libtools/signals.c:575`（`db && !TF` 直回）、`:922`、`:988`（SMC/hotpage） |
| 6 | **主信号返回路径不调用它**：`siglongjmp` 分支与正常返回都不写回宿主槽 | `signals.c:580-607`、`:632`；主入口 `:1315`/`:1355` 调用 oldcode 后直接 `return` |
| 7 | 探针 `curdb=0` ⇒ 那 3 个分支一个都没走 ⇒ 宿主 `regs[26]` 全程未更新 | `a0_trace/efl_probe.log` |
| 8 | 0.3.0 **全源码无** `regs[26] =` 写入、也无 `copyEmu2USignalCTXreg`；它靠单层 `emu->eflags = sigcontext[X64_EFL]` + `siglongjmp` 回主循环用 emu 重建 | 0.3.0 `signals.c:1297`、`:1270` |
| 9 | `mctx2emu()` 会同步 EFL；`emu2mctx()` 初始化 EFL 为 `emu->eflags \| RF` | `sigtools.c:796/820` 区、`:780` 区 |

### 10.2 为什么 E7 / E9 的补丁点无效（源码解释）

- **E7（内层 `:566` 之后同步 TF）是冗余的**：`memcmp != 0` 时 `:570` 的
  `mctx2emu()`（`db || emu->jmpbuf`）或末尾 `:632` 已经把 emu EFLAGS 设成
  Wine 修改后的 sigcontext 值，E7 没有新增语义。
- **E9（外层 `:747 GO(eflags)` 之后写回 TF）在关键路径上根本不执行**：
  内层 `emu->jmpbuf` 非空时走 `:605 siglongjmp`，直接跳到
  `dynarec.c:228` 的 `SigSetJmp`，**不返回外层** `my_sigactionhandler_oldcode`，
  外层补丁被整体绕过。
- 两条路径下 `emu->eflags` 按源码都应是 TF=0，但实测 guest 仍 TF=1
  ⇒ **还有第三个机制**没被覆盖；这不是「再修一层 EFLAGS 恢复」能解决的。

### 10.3 唯一未在正确构建配置下验证过的 0.4.4 新机制：`no_tf`

- `signals.c:588` 与 `:633` 的 `emu->flags.no_tf = 1;`（0.3.0 无此字段/逻辑）。
- 语义是「信号返回后首条指令跳过一次 TF 陷阱」；若 `no_tf` 未被正确消费/清零，
  guest 会在每条指令后重复 TRAP —— 与日志 `TRAP trap=1 tf=1` + `STEP_END pend=9`
  无限循环吻合。
- **历史上的 r112c（删 4 处 `no_tf` 写点）只在 ntf 树编过**：该树
  `ARM_DYNAREC=OFF`、linker 为空（§7.2），二进制在容器里根本起不来，
  所以 `no_tf` 从未在作者版配置上被单独验证。E4 只测了 r112d，E7/E9 只测 EFLAGS 恢复。
- ⇒ `no_tf` 是目前**唯一有源码依据、且尚未被正确实验证伪**的变量。
  （注意：这是候选，不是定论；10.2 里「emu->eflags 应为 TF=0」与实测的落差
  也说明我们对 siglongjmp 恢复点/宿主槽的交互仍不完整。）

### 10.4 下一步：一个实验即可定性

在**作者版配置**上只删 `signals.c:588`、`:633` 两处 `no_tf` 写点
（`signal32.c` 的两处因 `BOX32=OFF` 不参与构建，可不动），
编 `box64_notf.so`，跑 E10 对照 B：

| 结果 | 结论 |
|---|---|
| `hits` 从 25 恢复（≈384） | 根因确定，继续升版并做性能 A/B |
| 仍 `hits=25` | 0.4.4 的 TF 链需要上游级重构，按 §4 止损条件终止 |

在此之前不再叠 EFLAGS 补丁。设备本轮**未部署**，仍是生产态。
