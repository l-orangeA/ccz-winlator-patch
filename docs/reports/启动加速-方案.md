# 启动 50 秒的构成与缩短方案

日期：2026-11-02　测量环境：Winlator 8 + container ccz22，AMD64→ARM64 翻译由 box64 承担。

## 一、先把 53 秒拆开（实测，不是估计）

| 阶段 | 耗时 | 怎么量的 |
|---|---|---|
| Android 拉起 Activity + 容器/X 服务/wineserver 启动 | **~7.1 s** | 用一个只建空窗口的小 exe（`waitwin.exe`）走同一条 intent 启动，屏幕从"全黑"到"出现窗口"的时间 |
| 壳（VProtect）的解密/反调试自举 | **~46 s** | ntdll 里给每次断点装载打时间戳：第 1024 次装载时 t=30.2 s，全程共 1600 次 ⇒ 约 46~47 s |
| 解包完成 → 标题画面 | **<1 s** | 两者相减 |

**结论：53 秒里 46 秒是壳自己的活，7 秒是容器启动。** 我们自己那套硬件断点补丁只占 1.3~4.4 s（4.4 万次异常）。

## 二、方案（按性价比排序）

### A. 不退出游戏，用"切后台"代替"关掉"——0 改动，见效最快
- 实测：切到桌面再切回来，**3.0 秒**回到游戏画面（对比冷启动 53 秒）。
- 前提是进程不被系统杀掉：MIUI 里把 Winlator「锁定」（最近任务下拉加锁）+ 关闭它的省电限制（电池 → 应用省电策略 → 无限制）。
- 缺点：还是占着内存（Ekd5 ~700 MB + 容器 1 GB 级），玩别的重负载游戏时可能被回收。

### B. 只省"容器启动那 7 秒"
- 现状是每次 `force-stop` 整个 app，容器、wineserver、X 全重启。
- 如果能"容器常驻 + 只重启游戏进程"，能省 7 秒（53 → 46 秒），但 Winlator 的会话模型是"一个程序退出 = 容器结束"，
  要做到得自己挂一个常驻进程并绕开它的会话管理，收益 13%，性价比一般。
- 另外可顺手做的：启动选择改"激进（启动时停止服务）"、关掉用不到的 wincomponents（direct3d/directsound/directmusic/xaudio），
  预计还能省 1~3 秒，零风险。

### C. 让 box64 把壳的 VM 跑得更快——已基本吃干
- 安全开关已试遍（BIGBLOCK=3 / FORWARD=1024 / CALLRET=1，收益 2~5%）；
  `SAFEFLAGS=0`、`FASTNAN/FASTROUND=1` 会让游戏不出窗口。
- 46 秒是纯 x86 指令翻译量，再快只能改 box64 的 dynarec（高风险、且前面已证明异常开销只占 3~8%，改它收益有限）。

### D. 脱壳一次，之后直接跑解包后的镜像——唯一能"去掉 46 秒"的路
- 思路：抓一次壳解密完成后的镜像（OEP + 修复 IAT/重定位），做成一个不需要壳的 exe，之后启动 ≈ 容器 7 秒 + 游戏初始化 1~2 秒。
- 代价与风险：
  1. 是一个完整的脱壳工程（找 OEP、dump、IAT 重建、可能的自校验/反 dump 处理），不是几小时能稳的活；
  2. 改出来的镜像若触发壳的完整性校验，可能直接崩；
  3. 属于**绕过软件保护**，只适合自己有正版、自己在本机用的场景，不能分发。
- 建议：先做"可行性探针"——在壳解密完成后 dump 进程镜像，用 `dumpbin/objdump` 看 OEP 处代码是否已是可执行的正常 x86，再决定要不要投入。

### E. 进程快照/恢复（CRIU 式）
- 解包完成后把整个 Wine 进程组快照，下次直接恢复 —— 理论最优，但 Android 上没有 CRIU、需要 root/内核支持。
- **不可行**，列出来只是说明"为什么不能一步到位"。

## 三、顺带发现的一个可靠性问题（重要）

把 `cpuListWoW64` 设成**单核（cpu7）**时，最近 5 次启动里有 **2 次卡死**：
进程状态 `t (tracing stop)`，`TracerPid` 指向 proot（libtinyproot.so），而 proot 自己阻塞在 `wait4`。
典型的多线程饥饿死锁——所有 32 位线程挤在一个核上，tracer 和 tracee 互相等。

改回 `4,5,6,7` 后连续 **3/3 正常**（52.2 / 53.0 / 55.8 s）。
**建议不要用单核**：单核只让游戏自身 CPU 降 26%，但总 CPU 不变、启动更慢，还会显著提高卡死概率。
