## 1. 问题重述：我们其实不需要「修好 Dr」

- 壳用硬件断点模拟保护壳代码，`NtSetContextThread` 设 Dr、等待访问命中、再单步。
- 0.4.4 下 Dr1 被污染成 `ffce115f`，`hwbp_match_write` 永不命中，壳卡在 re-arm 循环（`hits=25`）。
- 根因已追到「非显式写入」，需要 gdb watchpoint，proot+Android 做不到（§20）。
- **换思路**：不让壳「看到」脏 Dr，比「找出谁写脏」便宜得多。

---

## 2. 路线 A：Wine 层 Dr 白名单过滤（推荐）

### 2.1 依据

SETPROBE（§18）里壳通过 32 位 Set 设置的 Dr1 全部是：

```
31ef00 / 31efbc / 31f000 / 31f010 / 31f014   （都在 0x31xxxx，< 0x80000000）
```

而唯一的异常值 `ffce115f` **从未出现在任何 Set 里**（WCTX 0 次、WCTX64 0 次、SETPROBE 0 次），
是 Get/缓存侧冒出来的垃圾。`0xffce115f >= 0x80000000`，明显越出 32 位用户态栈区。

### 2.2 实现（两处，各 3 行）

在 `get_thread_wow64_context`（`signal_x86_64.c:1408` 之后）和
`NtGetContextThread` 的 64 位路径（`:1242` 附近）返回前：

```c
/* DRF: reject out-of-range Dr values (32-bit user space is < 0x80000000).
   Observed garbage ffce115f comes from an unknown write; the shell only ever
   sets 0x31xxxx, so substituting the last known-good value is safe. */
if ((uintptr_t)context->Dr1 >= 0x80000000UL)
    context->Dr1 = amd64_thread_data()->dr1;   /* last good, or 0 */
if ((uintptr_t)context->Dr7 >= 0x80000000UL)
    context->Dr7 = amd64_thread_data()->dr7;
```

要点：
- 只过滤 `Dr1/Dr7` 两个壳实际使用的寄存器，不动 Dr0/Dr2/Dr3；
- 替换源用 `amd64_thread_data()` 缓存（上次合法 Set 写入的值），不是硬编码；
- 放在 **Get 返回给壳之前**，这样壳读到的 Dr、后续 Set、`hwbp_update` 三处一致。

### 2.3 风险与验收

| 风险 | 评估 |
|---|---|
| 壳真的想监视 `>=0x80000000` 的地址 | 证据显示不会（SETPROBE 0 次） |
| 掩盖症状、根因仍在 | 是；但目标是「让 0.4.4 跑起来」，不是「修 Wine」 |
| 影响 64 位程序 | 只在 32 位 Get 路径过滤，64 位不受影响 |

验收：**E22 `hits≈384`** → 出标题 → 性能 A/B。半天内可出结果。

## 3. 路线 B：换 Wine 10.10（真正的「重构」）

### 3.1 依据

WSL 已有 `/root/wine1010`（**Wine 10.10**），并且带
`dlls/wow64` / `dlls/wow64cpu` / `dlls/wow64win` —— 这是**微软式的新 wow64 架构**，
32 位上下文转换由独立的 `wow64cpu` 层处理，不再走 9.2 的 `set_thread_wow64_context_inner`。
Dr 污染很可能在新架构里已不存在（或表现不同）。

### 3.2 实施

1. 编 Wine 10.10 的 `ntdll.so` / `win32u.so` / `wineserver`（ARM64，作者版配置）；
2. 与 Winlator 8.0 的 imagefs 做兼容性替换（win32u 接口、X11 驱动、字体/注册表）；
3. 保持 box64 0.4.4 作者版 + 现有容器配置；
4. 跑 E23：`hits` → 出标题 → 性能。

### 3.3 风险

| 风险 | 说明 |
|---|---|
| win32u 接口不兼容 | Wine 10 的 win32u 可能与 Winlator 8.0 的驱动层不匹配，需要一并替换 |
| 新 wow64 更重 | `wow64cpu` 有额外转换开销，可能吃掉 0.4.4 的收益 |
| 未知回归 | 字体/输入/音频/网络都可能出问题 |

工作量 1–2 天；若 A 成功则不必做。

## 4. 路线 C：backport 0.4.4 dynarec 到 0.3.0（不推荐）

- 保留 0.3.0 的信号层（Dr 正常），只移植 0.4.4 的性能改进。
- 但 §2 的差异盘点已证明：DynaCache、hotpage、custommem 三态与信号层/dynarec 双向耦合，
  可单搬项（BIGBLOCK、`is_addr_autosmc`、BUILD_PASS、`updateflags_arm64*`）收益估计 <5%。
- 数周工作量换 <5%，不划算。

## 5. 路线 D：patch 壳（不推荐优先）

- 需要把壳从设备拉到 PC（300 MB+），逆向找 hwbp 检测点并 patch PE。
- 强壳通常有校验/自校验，patch 后可能直接拒绝运行。
- 只有在 A/B 都失败、且用户愿意投入逆向时才考虑。

## 6. 路线 E：0.3.0 解包 + 0.4.4 运行（不可行）

- box64 是进程级引擎，同一个 Wine 进程无法中途换 box64；
- 除非壳支持「解包后 dump 成独立 exe」，未验证且大概率不支持。

## 9. A 实施结果（2026-11-08 15:3x）：白名单过滤无效

`build/ntdll_drf.so`（`b8314128`）= fix110c + 在 32 位 `get_thread_wow64_context`
写缓存前过滤 `Dr1/Dr7 >= 0x80000000`（替换为缓存上次合法值）。E22 实跑：

```
arms=2240  faults=19973  steps=18541  hits=25
```

**`hits` 仍为 25，无改善。** 两种解释：

1. 壳并不依赖 `GetContext` 返回的 Dr 值（它更可能只信 Set 的返回值 / 自己的记录），
   所以挡住脏值不影响它的状态机；
2. 过滤生效了，但 `hits` 冻结另有原因（TF/单步链），Dr 只是表象。

无论哪种，**A 路线到此证伪**，不再在 Dr 值上做文章。

## 10. B 启动（2026-11-08 15:3x）：Wine 10.10 原编译

### 10.1 关键事实纠正

设备上的 Wine **不是 ARM64**：

| 文件 | e_machine |
|---|---|
| `build/ntdll_fix110c.so` | `0x3e`（x86-64） |
| `build/ntdll_drf.so` | `0x3e`（x86-64） |
| `unpack_tools/box64_044_glibc231` | `0xb7`（AArch64） |

即：**Wine 的 host 侧 .so 是 x86-64，由 box64（ARM64）翻译执行**。
所以 Wine 10.10 无需 ARM64 交叉编译，直接在 WSL（x86_64）原编译即可 —— 与 9.2 的
`--enable-archs=i386,x86_64` 配方完全一致。**B 的工作量从「1–2 天」降到「几十分钟编译 + 替换测试」。**

### 10.2 进展

| 步 | 状态 |
|---|---|
| `./configure --enable-archs=i386,x86_64`（沿用 9.2 的最小依赖配方） | ✅ 成功（exit 0） |
| `make -j8 dlls/ntdll/ntdll.so dlls/win32u/win32u.so server/wineserver` | ⏳ 后台编译中 |
| 替换测试（E23） | 待编译完成 |

### 10.3 预期风险

- Wine 10 的 `wow64/wow64cpu/wow64win` 是**新的 32 位 PE 模块**，可能还需要一并部署
  `wow64.dll` / `wow64cpu.dll` / `wow64win.dll`，否则 32 位壳起不来；
- `win32u.so` 与 Winlator 8.0 的 X11/图形驱动接口可能不兼容，需要回退或补丁；
- 字体/输入/音频可能有回归，先只验 `hits`。

### 10.4 验收

**E23 `hits≈384`** → 出标题 → 性能 A/B。若 Wine 10.10 下 Dr 污染消失，则 0.4.4 真正可用。

### 11.2 E23 结果

作者版 box64 + Wine 10.10 三件套，prod env：

```
进程直接退出（<50 s），无任何 hwbp_stats
```

`logcat` 无 Wine/box64 相关错误（Winlator 的容器日志不走 logcat）。

### 11.3 推断

只换 ntdll/win32u/wineserver **不够**，Wine 10 至少还缺：

1. `libwine.so`（Wine 10 的宿主运行时，符号/版本可能不兼容 9.2）；
2. **新的 wow64 PE 模块**：`wow64.dll` / `wow64cpu.dll` / `wow64win.dll`
   （Wine 10 的 `dlls/wow64*` 是新架构，32 位壳依赖它们做 CPU 转换）；
3. Wine 10 格式的注册表/前缀（`wineboot` 需要重建，旧前缀可能不认）。

### 11.4 下一步（1–2 天工程，非一次会话）

1. 编全量 Wine 10.10（`make -j8`，不只是三件套），取 `libwine.so` 与 wow64 三件套；
2. 整套替换 `files/imagefs/opt/wine/`（保留备份），`wineboot -u` 重建前缀；
3. 先跑 `wine notepad`/探针 exe 验证 32 位基本可用，再上壳；
4. 通过后跑 E23 → 出标题 → 性能。

### 11.5 阶段结论

- **A 证伪**（Dr 白名单不影响 `hits`）；
- **B 可行性已被证实**（Wine 10.10 能编、能部署），但**不是三件套能换的**，需要整套 Wine 10 + 新 wow64 模块 + 前缀重建；
- 这是 1–2 天工程，适合作为独立任务排期，而不是继续在本会话里试错。

设备已恢复 0.3.0 生产态（四件套 md5 全对）。
