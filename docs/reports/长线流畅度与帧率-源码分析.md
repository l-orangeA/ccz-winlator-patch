## 2. 已有实证（重读，不重复劳动）

### 2.1 长线流畅度 —— 根因是调度不是算力

`2026-11-06_渲染与卡顿攻坚日志.md` §2（23.4 分钟 ftrace，130 s 分析窗口）：

| 指标 | 数值 |
|---|---|
| 游戏主线程 | **7.4% 在 runqueue**、29% 睡眠；工作形态 **1 ms 小突发**，单次上核中位 0.23 ms / p99 2 ms |
| 落核 | 55% 在 cpu6；**卡顿起点 cpu6 = 400 MHz（最低档）**，卡顿过程中才爬到 600–1100 MHz |
| 大核 | 中位 600 MHz；prime 1.2–2.6 GHz；`migration/6` 迁移线程在跑 |
| **FPSGO 目标帧率** | **10–60 之间乱跳** |
| 渲染链（GL+X+SF+composer） | 合计 ~4.5%；**CPU 空闲 58%** |
| 累积退化 | 15 次连续开/关范围：**线性、无退化**；Native Heap / Dalvik / VmRSS 全不变 ⇒ **无内存/句柄泄漏** |

⇒ 日志原话：**「卡顿根因是游戏单线程 1 ms 突发 + 大核 DVFS 长期 400–600 MHz + 频繁跨核迁移」**。
§2.4 排除了「长线 = 内存泄漏」这一常见假设。

### 2.2 帧率 —— 卡在呈现端

| 指标 | 数值 |
|---|---|
| 平均内容出帧 | 24.2 fps；帧间隔中位 10–16 ms；**p90 28–200 ms** |
| 每 5 秒窗口 | 6–21 次 >50 ms 空档 |
| 游戏待机 | ~100 次内容更新/秒；**SF 直出约 56 帧/秒**（`apk/README.md:198`）⇒ 瓶颈在呈现端 |
| X 协议稳态 | MIT-SHM PutImage **92 次/秒**（均 28.5k px）、`SetClipRectangles` **388 次/秒**；逐像素转换只占 2–3% |

### 2.3 已生效的优化（别重复做）

- `fr60`：`XServerView.surfaceCreated` → `Surface.setFrameRate(60f, 1)`（FIXED_SOURCE）→ 大核中位 **600 MHz → 2.0–2.65 GHz**，游戏 CPU 34%→22%、App 30%→8%；自动战斗 29.5 fps / p90 49.9 ms。
- `glpin`：`GLRenderer.onSurfaceCreated` → `taskset -p f0`（cpu4–7）→ GLThread 从小核迁入大核，runqueue 3.4%→1%，滚动 6 s 游戏 2.90→2.17 s。
- `Process.setThreadPriority(-4)`（`GLRenderer.onSurfaceCreated` / `XConnectorEpoll.run`）。
- `nomove`：`XServer.injectPointerMoveDelta` 零增量早退。
- **残留问题**：卡顿起点仍 400–500 MHz（突发之间掉频再爬升）、游戏线程 runqueue ~9.8%、跨核迁移未消除。

### 2.4 已判负 / 别再试

| 项 | 结论 |
|---|---|
| `Surface.setFrameRate(120f,1)` | 不崩但 56.6 fps ≈ 直出 56.4，**无差别**；`Window.setFrameRate(120f)` 在这台 vivo **NoSuchMethodError 启动即崩** |
| 合帧 `GLRendererCoalesce` | 当时带轮询探针干扰，出帧压一半但数据不可比，**未采用**（干净场景可重测，见 P3） |
| 上传减半 / 脏矩形 | 同场景 0.327/0.338 vs 全量 0.306/0.345，**无收益** |
| `ClientSideGraphics=N` | 标题栏/图标花屏，已回滚；Winlator **必须** client-side 图形 |
| A1 `memset→libc` win32u 重编 | 0.447 vs 0.442 s/次，±1% 噪声内，**零收益** |
| swap0（11.2 原样）/ 原生光栅移植 | p90 91–141 ms 判负 / 帧间隔在噪声内 |
| box64 0.4.4 / 0.3.8 | 破坏 VProtect 反调试；0.3.0 才正常 |
| ext4 迁移、分辨率、图形驱动、CPU 亲和微调 | 均判「不是瓶颈」或噪声内 |

> 关键线索：`120f` 无效而 `60f` 有效 ⇒ 收益**不是「提高帧率」，而是给 MTK FPSGO 一个稳定的固定源目标**，止住 10–60 乱跳。这决定了 P3 的方向。

## 3. 源码链路（file:line）

### 3.1 帧率 / 呈现链

| 位置 | 内容 |
|---|---|
| `out8/sources/com/winlator/widget/XServerView.java:24` | **`setRenderMode(0)` = `RENDERMODE_CONTINUOUSLY`** —— GL 线程按 vsync 持续绘制 |
| `renderer/GLRenderer.java:170-171` | `onUpdateWindowContent(Window) → requestRender()` |
| `renderer/GLRenderer.java:196-199` | `onPointerMove → requestRender()`；另有 :154/:160/:166/:186/:192/:198/:314/:433/:447/:468 多处 |
| `renderer/Texture.java:50-63` | `updateFromDrawable` 仅在 `needsUpdate` 时做整张 `glTexSubImage2D` |
| `XServerDisplayActivity.java:573` | `new XServerView(...)`，用的是 `GLRenderer`（非 Coalesce） |

**推断（待验证）**：连续渲染模式下 `requestRender()` 全是 no-op；实际节拍 = 面板 120 Hz 连续绘制，而内容更新 ~100 次/秒、SF 只出 56 帧/秒 —— **渲染节拍、内容节拍、呈现节拍三者脱节**。这正是 FPSGO 目标乱跳的合理来源，也解释了 60f FIXED_SOURCE 为什么有效。

### 3.2 DVFS / 调度链（长线流畅度主因）

| 位置 | 内容 |
|---|---|
| `core/Win32AppWorkarounds.java:78-79` | `(short) ProcessHelper.getAffinityMask(container.getCPUList(true))` / `...WoW64(true)` —— **亲和掩码是 `short`** |
| `core/Win32AppWorkarounds.java:130-157` | `assignTaskAffinity(Window)`：仅 `isApplicationWindow()`；`processAffinity = isWoW64() ? maskWoW64 : mask`；经 `WinHandler.setProcessAffinity` 下发 |
| `core/Win32AppWorkarounds.java:292` | **`WINEOVERRIDEAFFINITYMASK`** env 注入（现有 workaround 用的机制）→ **零编译覆盖点** |
| `core/Win32AppWorkarounds.java:302` | `ProcessHelper.getLastCoreAffinityMask()`（钉最后一个核的现成实现） |
| `container/Container.java:578-601` | `getFallbackCPUList` / `...WoW64`：后者取后半核（4–7） |
| 实机 `cpuList` / `cpuListWoW64` | `0,1,2,3` / `4,5,6,7` |

⇒ 游戏进程目前被允许在 **cpu4–7 之间迁移**（日志 `migration/6`），而这 4 个核在 MT6985 上并非同构（1×X3 prime + 3×A715），频率/调频策略不同 → 突发落在不同核上，触发掉频再爬升。
日志 §「单核 `7` 不会被应用（仍 0–7），原因待查」—— **`assignTaskAffinity` 的下发链路与 `ProcessHelper.getAffinityMask` 实现是待读的第一处源码**。

### 3.3 Wine / X 客户端链（每帧固定开销）

| 位置 | 内容 |
|---|---|
| `wine0905/dlls/win32u/window.c:2013-2028` | `SERVER_START_REQ(set_window_region)`；先 `NtGdiGetRegionData` + `malloc` + server call + `free` |
| `wine0905/dlls/winex11.drv/bitblt.c:1875` | `x11drv_surface_set_region` → `XSetClipRectangles(..., YXBanded)` = **388 次/秒的来源**；注册于 `:2004` 的 surface funcs |
| `wine0905/dlls/winex11.drv/bitblt.c:1907` | `x11drv_surface_flush` → `copy_image_byteswap` + `XShmPutImage`/`XPutImage` + **`XFlush`**（92 次/秒） |
| `wine0905/dlls/winex11.drv/x11drv_main.c:81` | `client_side_graphics = TRUE`（必须保留） |

⇒ A5「update_dc 缓存」的精确落点已定位：`set_window_region` 的 server 往返 + `x11drv_surface_set_region` 的无条件重设 clip。**可加 「region 未变则跳过」缓存**；`XFlush` 合并是第二个候选（风险更高）。

### 3.4 硬约束

- `/root/box64-0.3.0src` 只有 `usr/local`（安装物），**没有可重建源码树** → 翻译层改不了；所有 box64 侧优化（rep-movs、dynarec 参数）只能靠 env 开关，且 README §20 已判「FASTREP 零差异」。
- `winex11.drv` / `win32u` 有 WSL 源码树 + canonical 重编配方（`build_win32u_r109f/r109g.sh` 已验证），**可改**。
- Java 层有 jadx 源码 + smali 补丁链（`patch_fr2.py` 等）+ testkey 同签名重签流程（`apk/README.md`），**可改**。

## 5. 验收口径与止损

1. **基线先行**：写回 `phone_container_20261106_prod.txt` 或明确记录当前漂移值，同一基线做所有 A/B。
2. **口径**：同存档、同场景、≥3 次；只认 >3 s / >5% 的差异（README §9）。单次波动 ±2 s。
3. **长线专项**（本轮新增，之前没做过）：**≥20 分钟连续运行**，按 5 分钟分段统计 p90、>80 ms 帧数、大核频率中位、`migration/*` 次数、电池温度 —— 专门看「是否随时间退化」，而不是只看单次峰值。
4. **环境控制**：停直播壁纸（`apk/README.md:202`）、插电、拔掉探针；ftrace 缓冲与采样脚本沿用 `tools/measure_render.py` / 日志 §2 方法。
5. **卡死簇**：出现「已知良好组合也 100% 失败、停滞点计数相同」→ `adb reboot` 复位（README §17.4/§18），**不在卡死态下结论**。
6. **止损**：单项收益 <5% 即停；出现花屏 / 启动失败 / 20 min 后 p90 明显恶化即回滚；每个包只改一个变量。

## 8. 实测补充（2026-11-09 21:4x）：可信基线与口径修订

### 8.1 可信基线（60 秒自动战斗，只读）

| 指标 | 值 |
|---|---|
| 逐秒出帧 | 12–65 帧，60 秒全活跃 |
| 平均 | **39.7 fps**（剔除首秒缓冲初值 38.2） |
| 帧间隔 | p50 **16.63 ms**、p90 **49.88 ms**、p99 **266.05 ms**、max **548.81 ms** |
| 长尾 | ≥80 ms 169 次、≥100 ms 135 次（2381 间隔中 5.7%） |
| 刷新率 | `frameRateOverride = 60.000004 Hz` 全程；系统 144 / 应用单独 144 未落到 app |
| 亲和/CPU | Ekd5 `4-7`（生效）、其余 `0-7`；Ekd5 0.3–0.4 core |

### 8.2 ★ 口径修订（重要，前面若干判断因此作废）

1. `dumpsys SurfaceFlinger --latency` 环形缓冲用 `9223372036854775807`（LONG_MAX）填充空位。
   **必须过滤 `1e12 < v[1] < 1e18`**；否则 `max(ts)` 被顶到 LONG_MAX，之后所有真实帧判为「已见过」，
   得到假的 0 fps。历史 `fps_probe.py` 有此上界，本日新脚本漏了，现已给全部脚本补回。
2. 必须取 `SurfaceView[...](BLAST)#NNN` **子层**；父层 `SurfaceView[...]#NNN` 的缓冲全 0。
3. `gfxinfo` 的 `Total frames / Janky / 99th` 统计的是 **HWUI UI 层**，不是游戏 GL 内容帧
   （180 秒内一格没动即证明）。游戏帧率只能用 BLAST 子层 `--latency`。
4. **作废结论**：本日早些时候「游戏静止 177 秒 / 0 帧 / 11 fps / p90 216ms / 5.4fps」等全部作废。
   两轮长采样里 35 次截图 md5 全不同，画面一直在动（自动战斗确实在跑）。

### 8.3 对 §4 候选与 §6 顺序的修正

- 基础节奏稳定 60Hz（p50 16.63ms），问题在 **p99 266ms / 每秒约 2.2 次 ≥100ms 尖峰**，
  与 §2.3 的 DVFS 掉频再爬升一致 ⇒ P1（亲和收窄）判据明确为 **p99 与 ≥100ms 次数**，辅以 p90 / avg fps。
- 「稳定 90/120」当前不可达：app 锁 60Hz 且 60 都不稳。P3 解 `Surface.setFrameRate(60f, FIXED_SOURCE)`
  锚定是前提；P1 压尖峰是第一步。

  容器用 `virgl + wined3d + pulseaudio` 通用栈；`cpuListWoW64=4,5,6,7` 下发到游戏进程**确实生效**。
