## 1. 机制梳理

### 1.1 壳（VProtect）的解包机制

| 项 | 事实 | 来源 |
|---|---|---|
| 反调试 | x86 硬件数据断点 `Dr1 = ESP+0xEC`、`Dr7 = 0x300104`（读写 1 字节） | README §3 |
| 解包规模 | `arms 64 → 1600`，共 **1600 步** VM 解释器循环 | `hwbp_stats` |
| 每步成本 | 纯 VM **4.42 ms/步**（拟合 0.00442362·arms） | 报告 §2.2 |
| 栈访问 | 解包期对栈页（`0x31f000`）共 **44,106 次**访问，只有 **400 次**落在 `Dr1=0x31f014` | `hwbp_stats` |
| 心跳校验 | 每次 arm 后必须在 `Dr1` 处看到 #DB，否则重 arm 或判定被调试 | `hwbp_push_delta` + `hwbp_match_write` |

### 1.2 补丁（fix110b）的页保护机制

单次页故障的完整成本链（`src/fix110b/virtual.c:4141` + `signal_x86_64.c:2615`）：

| 步 | 动作 | 源码位置 | 成本 |
|---|---|---|---|
| 1 | SEGV 产生 → **proot（tracer）停一次 → `PTRACE_CONT`** | proot 层，无源码 | 1 次 ptrace 往返 |
| 2 | `hwbp_rw_page_for(si_addr)` → `hwbp_handle_rw_fault`：`hwbp_match_write(addr)` 精确判断 idx，**解锁页**（`mprotect_range`） | `virtual.c:4133/4141` | 1 次 4 KB mprotect（含 TLB shootdown） |
| 3 | 两条路径二选一：<br>• push 类（`ESP == si_addr`）：回滚 ESP，`hwbp_step_begin` + 置 TF<br>• 其他：`hwbp_step_begin` + 置 TF | `signal_x86_64.c:2633-2652` | 极轻 |
| 4 | **TF 单步 → SIGTRAP → proot 再停一次** | proot 层 | 1 次 ptrace 往返 |
| 5 | `trap_handler` 的 `TF_STEP` 分支：<br>• 命中 400 次 → `dr6` + `hwbp_consume()`（页保持开放，**0 次 mprotect**）<br>• 误报 43,706 次 → `hwbp_step_end_ex(0)` **复保护** | `signal_x86_64.c:2751`、`virtual.c:4161` | 误报 1 次 mprotect |
| 6 | `setup_raise_exception`（仅 400 次真命中） | — | 轻 |

⇒ **误报单次 = 2 次 ptrace 往返 + 2 次 4 KB mprotect**；命中单次 = 2 往返 + 1 mprotect。
⇒ `hwbp_push_delta`、`hwbp_match_write` 都是纯 C 比较，**不是瓶颈**。

**关键结论（源码已确认）**：`hwbp_handle_rw_fault` 在 SEGV 阶段就已经精确判断了命中/误报（`idx` vs `9`），但**两条路径都必须走完「解锁 → 单步 → 复保护」**。原因是：
- 不解锁 → 指令重试必然再次 SEGV，死循环；
- 不单步 → 没有「指令刚执行完」的时刻可以复保护，页会长期开放 → 壳后续访问不触发 SEGV → 漏检。

⇒ 这 2 往返 + 2 mprotect 是**页粒度监视的必然代价**，除非换掉监视机制（见 §3.1 判死项）。

### 1.3 加载段（解包完成 → 标题）的机制

| 指标 | 实测（`boot_probe_20261111` io 轮） | 含义 |
|---|---|---|
| 墙钟 | 13.6 s（11-09 为 7.8 s） | 设备状态差异大 |
| `utime` / `stime` | 2.80 / **3.36 s** | **内核态 > 用户态** |
| CPU/墙钟 | 45% | 一半时间在等 |
| `Δrchar` | 11.1 MB | 读得很少 |
| `Δread_bytes` | **0** | 全在 page cache，**不是磁盘 I/O** |
| `Δsyscr` | **78,549** | 平均每次 **148 字节** |
| `majflt` | 321 | 缺页极少 |
| `vctx/s` | **5,101**（解包期 2,500） | 进程间等待翻倍 |

⇒ 加载段 = **海量小 read（Wine 逐文件/逐注册表键加载）+ client-server RPC + proot 路径重定向**，不是算力也不是磁盘。

### 1.4 容器启动的机制

`XEnvironment.startEnvironmentComponents()`（`out8/sources/.../XEnvironment.java:59`）是**串行 `while` 循环**：

```
FileUtils.clear(tmpDir)
  → SysVSharedMemoryComponent
  → XServerComponent
  → NetworkInfoUpdateComponent
  → VirGLRendererComponent
  → PulseAudioComponent
  → GuestProgramLauncherComponent（最后才拉 proot）
```

另有无条件动作：`WineStartMenuCreator.create`（`XServerDisplayActivity.java:467`）、`WineUtils.createDosdevicesSymlinks`（:468）、`FileUtils.clear(tmpDir)` 两次（:496 与 `startEnvironmentComponents`）。

已固化的跳过项：`wineprefixNeedsUpdate` / `generateWineprefix` / `changeServicesStatus` / `extractWinComponentFiles`（`startupSelection=1`）。

**M3a-9 的 10 分钟探测法**：在容器内跑一个最小 C 程序（交叉编译 aarch64），依次试：
1. `syscall(SYS_userfaultfd, O_CLOEXEC | O_NONBLOCK)` 是否返回 ≥0；
2. `UFFDIO_API` ioctl 是否成功（`features` 是否含 `MISSING`/`WP`）；
3. `UFFDIO_REGISTER` 一个 `PROT_READ` 页是否成功。
三步全过才值得投入；任一步 `EINVAL`/`EPERM` 即判死（Android 常把 `vm.unprivileged_userfaultfd` 设 0）。

## 12. 加载段探针：那 4.8 万次 read 不是文件 I/O（2026-11-12 22:10–23:40）

### 12.1 NtReadFile 探针

在 `dlls/ntdll/unix/file.c` 的 `NtReadFile` 注入计数器（fd→路径缓存 + 入口计数），阈值降到 256 次 dump 一次。

**结果：`rdprof.txt` 两次都没生成** ⇒ `NtReadFile` 全程调用 **< 256 次**。

⇒ **那 7.9 万次 read 根本不是文件读**。

### 12.2 那是什么

结合已有证据：

| 证据 | 指向 |
|---|---|
| `NtReadFile` < 256 次 | 不是文件 I/O |
| `vctx` 5,101/s（解包期 2,500） | **进程间上下文切换翻倍** |
| `stime` 3.36 s > `utime` 2.80 s | 时间在内核态 |

⇒ **4.8 万次小 read 是 wineserver 的 client-server RPC 往返**（每次 ~110 字节的请求/响应报文）。

### 12.3 `WINEFSYNC=1` 实测（想减少 RPC 往返）

| 轮次 | load（`title − unpack`） |
|---|---|
| 基线（`WINEESYNC=1`） | **6.9 s** |
| `WINEFSYNC=1`（叠加） | **8.6 / 9.3 s** |

⇒ **负收益 +1.7~2.4 s**。futex 路径在当前内核/负载下比 esync 慢。

### 12.4 结论

**加载段的 6.9 s 无法优化。** 它由两部分构成：
- **3.2 s：wineserver RPC** —— 减少它只能靠改 Wine 的 server 协议（不现实）；
- **1.8 s：数据加载**（46 MB `Ekd5.exe` + 36 MB `E5`）—— 必要开销。

至此，**全部 5 个段都已定位到机制，且都没有安全可拿的空间**。

**这是 5+ 年社区积累的 ARM64 JIT 编译器**，不是「一个模块」。

### 13.3 效率损失（估算）

- 原生 aarch64 跑 3,000 万次「乘加 + 查表」循环：**207 ms**（实测）；
- box64 在 app 域起不来（`lscpu` 缺失、`BOX64_CPUNAME` 绕不过），**本项目内无法直接基准对比**；
- 业界共识 box64 效率为原生的 **1/3~1/5**。

⇒ 7.1 s 对应原生约 **1.4~2.4 s**，**重写上限 = 省 4.7~5.7 s**。

### 13.4 为什么不能做

| 障碍 | 说明 |
|---|---|
| **工程量** | 36,945 行 JIT 后端重写 = 人年级别；且要覆盖全部 x86 指令语义 |
| **VProtect 反调试** | box64 0.3.8/0.4.4 已实证破坏壳（攻坚日志 §873-894）；任何 JIT 改动都要重新验证壳的 TF 单步/Dr 语义 |
| **收益不确定** | 即使效率翻倍（1/5 → 1/2.5），也只省 2.8 s，且要重测全部兼容性 |
| **已有实证反例** | 本项目试过的所有 dynarec 参数（`STRONGMEM`/`FORWARD`/`WAIT`/`BIGBLOCK`）**全部持平或负收益**——说明瓶颈不在「JIT 参数」，而在「x86 语义翻译的固有成本」 |

### 13.5 替代方案对比

| 方案 | 潜在收益 | 工作量 | 判定 |
|---|---|---|---|
| 重写 box64 dynarec | 4.7~5.7 s | 人年 | ❌ 不可行 |
| **FEX-Emu**（x86_64→ARM64，效率高于 box64 约 20~30%） | 1.4~1.7 s | 需重写全部 `hwbp_*` 补丁 + 验证壳 | ❌ 性价比不足 |
| box86（32 位专用） | 不确定 | 需换 32 位 Wine + 重写补丁 | ❌ Wine 10 已放弃 32 位 prefix |
| 优化 box64 现有路径 | 0 | — | ❌ 参数已试尽 |

### 13.6 结论

**方案 4 不做。** 纯 VM 的 7.1 s 是「壳的 VM 解释器在 x86 语义下的固有工作量」×「box64 的翻译效率」，两端都动不了：
- 壳的算法量是固定的（1,600 步 × 每步上千条 x86 指令）；
- box64 的翻译效率靠参数调不动（已试尽），靠重写不现实。

**这不是「没找到方法」，是「方法存在但成本远超收益」。**
